# nmon_analyzer.py — инструкция по анализу файлов NMON

Однофайловый скрипт на Python ≥ 3.12 (только стандартная библиотека) для анализа файлов
`nmon` (nmon for Linux) с узлов кластера Apache Ignite 2.17–2.19. Скрипт отвечает на вопросы
о поведении ОС на узле и в кластере: CPU, память, подкачка, диски, файловые системы, сеть,
процессы и JVM, качество самих данных nmon, сравнение узлов между собой.

Инструкция написана для ИИ-агента, который вызывает скрипт из shell. Структура:

## 1. Быстрый старт (рецепт для агента)

```bash
# 0. Какие команды есть и какой вопрос какой командой решается
python3 nmon_analyzer.py questions

# 1. Что за файлы: хосты, периоды, интервал, есть ли TOP/UARG, разрывы
python3 nmon_analyzer.py info /path/to/nmon/            # каталог со всеми файлами кластера

# 2. Можно ли доверять данным
python3 nmon_analyzer.py check node01.nmon

# 3. Общая картина по одному узлу: ключевые показатели + замечания (CRIT/WARN/INFO) + таймлайн
python3 nmon_analyzer.py report node01.nmon

# 4. Кластер целиком: покрытие, различия конфигурации, метрики по хостам, выбросы, синхронные события
python3 nmon_analyzer.py cluster /path/to/nmon/ --format md

# 5. Углубление в конкретную подсистему
python3 nmon_analyzer.py disk node01.nmon
python3 nmon_analyzer.py java node01.nmon
python3 nmon_analyzer.py mem node01.nmon

# 6. Что происходило в момент времени из лога Ignite (все метрики, процессы, диски, сеть)
python3 nmon_analyzer.py at --time "2026-03-14 03:52" node01.nmon

# 7. Ряд метрик вокруг инцидента, с укрупнением до 5 минут (max в корзине)
python3 nmon_analyzer.py timeline --around 03:52 --window 30m --step 5m --agg max node01.nmon

# 8. Что изменилось между «до» и «во время»
python3 nmon_analyzer.py compare --a 02:00-02:30 --b 03:30-04:00 node01.nmon

# 9. Машиночитаемый вывод
python3 nmon_analyzer.py health node01.nmon --format json
```

Порядок аргументов: пути к файлам ставьте **до** списковых опций `--metrics`/`--columns` (или отделяйте `--`),
иначе argparse примет путь за имя метрики. Скрипт возвращает в список путей завершающие элементы `--metrics`,
если они существуют как файлы, но надёжнее сразу писать `timeline node01.nmon --metrics cpu.busy disk.write`.

Рекомендуемый порядок при разборе инцидента: `info` → `check` → `cluster` (если файлов много) →
`report` по подозрительным хостам → `health`/`events`/`at`/`timeline`/`compare` → `disk`/`mem`/`vm`/`net`/`java`
по подсистеме, на которую указывают замечания → `export` для собственных вычислений.

Каждое замечание (finding) содержит код правила, значение, порог, факты с временем и подсказку, что это
обычно означает для Ignite. Замечания можно цитировать в отчёте RCA как есть.

## 2. Входные данные

- Аргументы `paths`: файлы `*.nmon`, каталоги (обходятся рекурсивно, берутся файлы с расширением
  `.nmon`, `.nmon.gz`, `.nmon.txt`, `.nmon.csv`) и маски (`*.nmon`, `**/*.nmon` — раскрываются самим скриптом,
  поэтому их можно передавать в кавычках, не полагаясь на shell).
- Файлы `.gz` читаются напрямую.
- Если в одном файле несколько запусков nmon подряд (дописанный файл, `cat a.nmon b.nmon`), второй и следующие
  запуски распознаются по повторному `AAA,progname` или повтору `ZZZZ,T0001`; их снимки получают суффикс
  `#N` и не смешиваются с первым запуском (`info`/`check` сообщают об этом). AAA и BBBP следующих запусков
  хранятся отдельно и не дописываются к конфигурации первого: `info` показывает таблицу «Файлы хоста и запуски
  nmon в них» (период, boottime, uptime, CPU, MemTotal, OS каждого запуска), `check` предупреждает о смене
  boottime (перезагрузка ОС) и конфигурации между запусками. Строки каждого запуска раскладываются по заголовку
  **своего** запуска: если после перезагрузки изменился набор дисков, интерфейсов или ФС (другие колонки
  DISK*/NET/JFSFILE), значения не сдвигаются по колонкам первого запуска; `check`/`info` пишут «запуск #N:
  заголовок секций … отличается от первого запуска; новые колонки / исчезли …». Если запуски в одном файле сняты
  с **разных хостов** (`AAA,host` различается — например, `cat` файлов двух узлов), файл делится по запускам
  (`файл#1`, `файл#2` …) и каждый запуск анализируется как файл своего хоста (`WARN:` в stderr, INFO
  `DATA_QUALITY` в `health`).
- Файлы группируются по имени хоста из строки `AAA,host`. Несколько файлов одного хоста **объединяются**
  в один ряд по времени; перекрывающиеся периоды (два nmon одновременно, или файл суток + короткий файл)
  дедуплицируются — в отрезке, который покрывает запуск nmon более раннего файла (от его первого до последнего
  снимка ± полинтервала большего из двух интервалов), остаются только снимки этого файла: снимки двух nmon с
  разной фазой или разным `interval` не чередуются и не учитываются дважды. Если `AAA,interval` различается по
  файлам или запускам (например, 60 с и 10 с), объёмы, длительности, «время выше порога» и разрывы считаются по
  интервалу каждого снимка (его файла/запуска; без `AAA,interval` — по медиане его шагов), а `health` выдаёт INFO
  `DATA_QUALITY` и `check` — INFO с перечнем интервалов. Число отброшенных дубликатов показывает `info`; `check` выдаёт WARN, если отброшено больше 10 %
  снимков какого-либо файла (с подсказкой про `--no-merge`), а если отпечаток машины (общие MAC/IP в ifconfig)
  подтверждает, что это копия файла той же машины, — INFO «файл дублирует другой файл того же хоста». Отключить
  объединение: `--no-merge` (тогда каждый файл становится отдельным «хостом» `host:имя_файла`; файлы с
  одинаковым именем в разных каталогах — `host:имя_файла`, `host:имя_файла#2` …; снимки разных файлов не
  дедуплицируются).
- Одинаковый `AAA,host` у разных машин (hostname не задан, клоны ВМ, контейнеры): перед объединением файлы с
  перекрытием периодов больше двух интервалов сравниваются по отпечатку из BBBP — MAC- и IP-адреса из
  ifconfig, а без ifconfig — MemTotal, модель и число CPU (lscpu), интерфейсы /proc/net/dev; кроме того,
  сравнивается boottime (расхождение больше 2 мин). Файлы делятся на группы по машинам: файл (по времени
  начала) входит в группу, ни с одним файлом которой не конфликтует, поэтому последовательные файлы одной машины
  по-прежнему объединяются. Если групп больше одной, каждая анализируется как `host:<первый файл группы>`, с
  предупреждением `WARN:` в stderr (с составом каждой группы) и в `check`/`info`. `--host` сопоставляется и с
  итоговым именем из вывода (`--host 'node01:b.nmon'`), и с `AAA,host` (`--host '^node01$'` оставит все группы).
- Обрезанный конец файла (файл скопирован, пока nmon ещё писал, или узел упал): последняя строка без перевода
  строки **отбрасывается** с предупреждением (её последнее поле может быть обрезанным числом); обрезанный или
  повреждённый `.gz` читается до места обрыва; последний снимок, в котором нет части секций предыдущего
  снимка или строк TOP (файл оборван перед ними), помечается как неполный в `check` (WARN) и `info` (сам снимок
  остаётся, отсутствующие значения — пустые; в сверке покрытия TOP он учитывается как ожидаемый пропуск); снимок,
  от которого в файле осталась только строка ZZZZ, отбрасывается; у секции, разбитой на
  продолжения (DISKBUSY + DISKBUSY1 …), строки последнего снимка без продолжения отбрасываются, чтобы суммы по
  дискам не считались по части устройств. Строка данных короче заголовка в последнем снимке запуска при полных
  остальных строках секции — обрыв записи: она не используется (все значения пустые); если короче заголовка и
  другие строки (заголовок длиннее данных: лишняя колонка в конце), все такие строки, включая последнюю,
  дополняются пустыми значениями с предупреждением.
- Поддерживаются: несортированные и отсортированные (`sort`) файлы — отсортированный файл поддерживается при
  одном запуске nmon в файле (порядок строк BBBP восстанавливается по их номеру: `sort` ставит `BBBP,1000`
  раньше `BBBP,101`): если в нём несколько запусков, строки разных запусков перемешаны и разделить их
  нельзя — каждый ключ (снимок, снимок+PID у TOP/UARG) берётся по первому вхождению, в stderr печатается `WARN:`,
  `check` выдаёт CRIT, а `health`/`report`/`cluster` — CRIT `DATA_QUALITY` (используйте исходные несортированные
  файлы); CRLF, BOM UTF-8 в начале файла, не-UTF-8 байты (заменяются),
  отсутствие ZZZZ (время оценивается по `interval` от известной метки или от AAA date/time своего запуска; `check`
  предупреждает, что реальные моменты снимков неизвестны; снимки, время которых оценить нельзя — нет ни ZZZZ, ни
  разбираемых AAA date/time, — не используются), испорченная метка времени (час > 23, минуты > 59) — строка
  считается нераспознанной (`check`: «нераспознанных или отброшенных строк»), время снимка оценивается по интервалу,
  продолжения секций DISKBUSY1/DISKREAD1… при большом числе дисков, старые версии nmon без колонок
  Threads/IOwaitTime в TOP, файлы с AIX-секциями (LPAR, POOLS…) — общая статистика по ним доступна через
  `raw.<SECTION>.<column>` и `export`, но Linux-правила health к ним неприменимы (`health`: INFO `NMON_AIX`); секция
  MEM формата AIX (без memtotal/memfree) в командах `mem`/`report`/`health` даёт сообщение вместо анализа памяти
  (`health`: INFO `MEM_FORMAT`). Файл без строк AAA/ZZZZ и известных секций пропускается как «не похоже на файл
  nmon»; файл только с заголовком (AAA, BBBP, заголовки секций, ни одного снимка) — «в файле нет ни одного
  снимка». Если часы шли назад внутри файла и метка снимка совпала с более ранним снимком того же файла, такой
  снимок отбрасывается, а `check` выдаёт WARN с их числом. Некорректные
  регулярные выражения в опциях, неверное время/длительность, окно с концом раньше начала, нечисловой порог в
  `--thr`, недоступный путь `--output` завершаются сообщением `ERROR: …` без трассировки и кодом возврата 3
  (раздел 8); внутренняя ошибка скрипта — трассировка и `ERROR: внутренняя ошибка …` с тем же кодом 3.
- Требования: Python 3.12+, без зависимостей; работает на Linux. Разбор — порядка секунды на 10 MB файлов
  (каждая команда разбирает файлы заново).

## 3. Общие опции (всех команд)

Все опции ниже есть у всех команд, кроме `questions` (у неё только `--format` и `--output`).

| Опция | Смысл |
|---|---|
| `--host REGEX` | оставить только хосты, чьё имя матчится (можно несколько раз) |
| `--from T`, `--to T` | окно времени. `T` = `YYYY-MM-DD HH:MM[:SS]`, `YYYY-MM-DDTHH:MM[:SS]`, `DD-MON-YYYY HH:MM[:SS]`, `YYYY-MM-DD` или просто `HH:MM[:SS]`. Метки из логов Ignite/GC принимаются как есть: дробные секунды (`03:52:10,123`, `03:52:10.123`) отбрасываются, обрамляющие `[ ]` снимаются; метка со смещением зоны (`Z`, `+03:00`, `+0300`) — `ERROR` (nmon пишет локальное время хоста без зоны: уберите смещение, при необходимости `--tz-shift`). Время без даты разрешается **один раз для всех хостов**: дата — от самого раннего снимка среди выбранных хостов; если данные переходят через полночь и время раньше начала — следующий день (так окно `--from 23:50 --to 00:20` одинаково для узла, стартовавшего до полуночи, и для узла, стартовавшего после). Если это время суток встречается в данных в разные сутки (данные длиннее суток), выводится `WARN` с выбранной датой — укажите дату явно. `--to` без даты при заданном `--from` берётся на дату `--from`, а если оно раньше `--from` и данные продолжаются в следующие сутки — на следующий день, как конец окна в `compare` (`--from '2026-03-15 04:00' --to 05:00` — час 15-го числа; окно `--from 23:00 --to 23:10` целиком до начала данных остаётся 10-минутным и даёт `ERROR` «нет снимков»). `--to` только датой — до конца этого дня (`--from 2026-03-14 --to 2026-03-14` = весь день) |
| `--around T --window D` | окно `T ± D` (по умолчанию `D = 10m`; форматы длительности: `90s`, `10m`, `2h`, `1d`); вместе с `--from`/`--to` — `WARN: --around перекрывает --from/--to` |
| `--format text\|md\|json\|csv` | формат вывода (по умолчанию `text`); в `csv` попадают таблицы, замечания и kv-блоки (у отчётов по хосту первая колонка — `host`; у колонок и ключей в KB, MB и секундах единица — в имени: `записано за период (KB)`), текстовые блоки пропускаются — раздел 8 |
| `--output FILE`, `-o FILE` | записать вывод в файл |
| `--top N` | сколько строк/пиков показывать там, где применимо (целое ≥ 1) |
| `--no-merge` | не объединять файлы одного хоста: каждый файл — отдельный хост `host:имя_файла` (одинаковые имена файлов — с суффиксом `#2`, `#3` …) |
| `--thr CODE=WARN[,CRIT]` | переопределить пороги правила health (см. раздел 6), можно несколько раз. Если CRIT не указан, берётся значение по умолчанию, но не «мягче» нового WARN (например, `--thr DISK_BUSY=99` даёт WARN 99 / CRIT 99); чтобы задать оба, пишите `--thr DISK_BUSY=99,100`. Код правила можно писать в любом регистре; порог — любое число (`5`, `.5`, `1e12`); неизвестный код, нечисловой порог или CRIT «мягче» WARN (`--thr DISK_BUSY=50,40`; у правил «↓» — CRIT больше WARN) — `ERROR: …`; для правил без числового порога (раздел 6) — `WARN: … значение не используется` |
| `--link-mbit N` | скорость **одного физического порта** в Mbit/s (nmon её не знает; число > 0): загрузка считается по каждому NIC и слейву bond относительно N, bond — относительно N × число его RUNNING-слейвов по ifconfig (слейвы без флагов — все), bond с одним активным слейвом — относительно N (`net`, `NET_LINK_UTIL`) |
| `--no-info` | не показывать замечания уровня INFO (в том числе замечания `check`; только вывод: итог CRIT/WARN/INFO, вердикт `check` и код возврата считаются по всем замечаниям) |
| `--min-severity CRIT\|WARN\|INFO` | показывать замечания не ниже уровня (в том числе кластерные в `cluster` и замечания `check`); как и `--no-info`, меняет только вывод — код возврата и вердикт считаются по всем замечаниям, о скрытых говорит примечание «показано N из M» |
| `--skip-first` | отбросить первый снимок каждого файла и каждого запуска nmon внутри файла (T0001 охватывает неполный интервал), если в ряду есть другие снимки. Первый снимок — по номеру `Tnnnn`, а не по самому раннему времени (часы могли идти назад); так же он исключается из статистики рядов (раздел 9): если кроме первых снимков в выборке ничего нет (файл из одного снимка, окно у старта nmon), они остаются, а примечания вместо «без первых снимков» говорят «T0001 не исключён … значения ненадёжны» |
| `--tz-shift ±D` | сдвинуть все метки времени, например `--tz-shift=-3h` или `--tz-shift=+02:00` — чтобы сопоставлять с логами в другой зоне (nmon пишет локальное время хоста без зоны). Значение с минусом передавайте через `=` |
| `--verbose`, `-v` | ход разбора в stderr |

Числовые опции проверяются: `--top` ≥ 1; `--limit` ≥ 0 у `timeline`, `export`, `bbbp` (0 — без ограничения) и ≥ 1
у `events`, `correlate`; `--window-snaps` ≥ 0 у `at` и ≥ 1 у `events`; `--z` и `--link-mbit` > 0; иначе — ошибка
аргументов (usage, `error: …`) с кодом 3.

Фильтр времени применяется ко всем командам, включая `health` и `cluster` (статистика считается только по окну;
исключения — то, что по узкому окну не определить, берётся по полному ряду хоста: фон и эпизоды выбросов в
`events` (показываются эпизоды, задевающие окно, целиком) и фон синхронных выбросов в `cluster`, обычный уровень
трафика (p75) для `NET_ZERO`/`NET_DROP`/`NET_BOND_MEMBER`, роли интерфейсов и состав bond, роль JVM
(основной/вспомогательный) и командные строки UARG; жизненный цикл JVM — паузы, исчезновение, старт и перезапуск
(`JAVA_ABSENT`, `JAVA_GONE`, `JAVA_START`, `JAVA_RESTART`, строки «до первого / после последнего появления» в
`java`, пометка «исчез» в `report`, разгон потоков после старта в `JAVA_THREADS_GROWTH`): край окна не считается
гибелью или стартом JVM — тот же PID после окна означает паузу, работавший до окна — не старт; замечание выдаётся,
если пауза, исчезновение или простой перезапуска захватывают окно (время события может быть вне окна, это сказано
в фактах); поправка avail по MemAvailable вычисляется один раз по опорному снимку файла BBBP). Процесс, который
есть в данных, но не виден в TOP окна, даёт `top.<cmd>.cpu` = 0, а не пустой ряд. Разрешённое окно печатается в
stderr строкой
`окно времени: A .. B`. Окно с `--from` позже `--to` — `ERROR: окно: --from (A) позже --to (B)`; если в окне нет
снимков ни у одного хоста — `ERROR` с окном и периодом данных каждого хоста, если только у части — `WARN` с их
периодами. Неразбираемое время (`25:00`, `2026-02-30`) — `ERROR` с перечнем форматов.

## 4. Справочник команд

Синтаксис: `python3 nmon_analyzer.py <команда> [опции] <paths...>`. Каждая команда, кроме `cluster` и
`questions`, выводит отдельный отчёт на каждый хост.

### `questions` — индекс вопросов
Печатает таблицу «вопрос → команда» и краткое напоминание общих опций. Не требует файлов.

### `info` — что это за файл(ы) и хост
Блоки: **Метаданные** (host, файлы, версия nmon, командная строка nmon с её опциями `-s/-c/-t/-T`, ядро,
boottime, заявленный и фактический интервал, число снимков, начало/конец, длительность, CPU, memtotal,
swaptotal, число дисков, физические диски, интерфейсы, число ФС, наличие TOP/UARG, отброшенные дубликаты,
число разрывов); **Файлы хоста и запуски nmon в них** — если файлов или запусков больше одного: файл, номер
запуска, начало/конец, снимков, boottime (из `AAA,boottime`, а без него — AAA date/time минус uptime из BBBP),
uptime на старте, CPU, MemTotal, OS; **Разрывы во времени** (если есть: от, до, длительность, где — «внутри запуска
nmon» или «между файлами/запусками nmon»); **Конфигурация (BBBP)** — модель CPU,
сокеты/ядра/потоки, NUMA, частоты, гипервизор, MemTotal/MemAvailable/Swap/HugePages/AnonHugePages/Committed_AS
на старте, uptime и load average на старте, дистрибутив; **Секции** (секции CPU показываются диапазоном
`CPU001..CPU064 (секций: 64)` по фактическим именам); **Предупреждения разбора** — таблица «файл, предупреждение»
(первые 20; в том числе обрезанная последняя строка, неполный последний снимок, отключённое объединение файлов,
смена заголовков секций между запусками).
В JSON memtotal/swaptotal — числа в MB, длительность (и в таблице разрывов) — в секундах, значения meminfo — в KB
(раздел 8). С `--tz-shift` boottime выводится со сдвигом, как все времена, а исходная строка `AAA,boottime` —
отдельной строкой «как в файле, без --tz-shift».

Как читать: «фактический шаг» ≠ `interval` или разрывы > 1.5×interval внутри запуска — хост зависал; разрыв между
файлами/запусками — nmon не работал (остановлен, перезапущен, перезагрузка ОС).
`TOP: нет` — nmon запущен без `-t`, анализа процессов не будет; если в файле есть только заголовок TOP (в файле
один снимок, а TOP пишется со второго), это сказано отдельно; если TOP в файле есть, но в окне
`--from/--to/--around` нет ни одного снимка с TOP (TOP пишется со второго снимка), выводится «в выбранном окне
нет снимков с данными TOP … расширьте окно». `UARG: нет` — без `-T`, флаги JVM недоступны. Разные boottime в
таблице файлов — узел перезагружался между файлами/запусками.

### `check` — качество данных
Перекрёстные проверки (сумма CPU_ALL ≈ 100 %; число CPU по трём источникам; среднее busy ядер ≈ CPU_ALL;
`VM pgpgout ≈ Σ DISKWRITE × шаг снимка`; `pgpgin ≈ Σ DISKREAD × шаг снимка` — обе без первых снимков файлов (T0001
охватывает неполный интервал); шаг — фактический, как у `export --agg sum` и объёмов `disk`/`net`
(после разрыва — длительность разрыва: приращение VM в первом снимке после разрыва покрывает весь разрыв, а DISK* —
скорость, усреднённая за него же), обе суммы — по одним и тем же снимкам; отношение печатается с 3 знаками и с
порогом 0.7–1.3 сравнивается напечатанное значение, при Σ DISK × шаг < 10 MB — «мало данных»; трафик каждого bond ≈ сумме
его слейвов, rx и tx отдельно (0.8–1.2; при нескольких bond слейв относится к bond с тем же MAC; состав,
подобранный по совпадению рядов, — «не применимо», на вердикт не влияет; если принадлежность части слейвов не
определена — одна строка «Σ всех bond ≈ Σ всех слейвов»); средний размер IO; постоянство memtotal; MEM ≈ /proc/meminfo; **размер страницы** (getconf PAGESIZE из BBBP,
без него — оценка по SReclaimable / nr_slab_reclaimable, иначе 4 KB) со сверкой PageTables из meminfo ≈
nr_page_table_pages первого снимка × страница (0.9–1.1); покрытие TOP (без TOP могут быть только первые снимки
файлов и неполный последний снимок); `Σ TOP MajorFault × шаг снимка` vs `VM pgmajfault` и `Σ TOP faults
(Minor+Major / Minor+2·Major) × шаг снимка` vs `VM pgfault` — см. ниже; оценка avail в снимке рядом с BBBP
минус MemAvailable ядра на старте — разность в MB и % RAM, норма −1…10 % RAM, отношение печатается справочно:
разница — резервы ядра, постоянные в MB, поэтому при малом avail отношение велико и без ошибки в данных),
список «мёртвых» колонок (всегда 0 / всегда N/A; значения −0.0 во всех снимках — метка nmon «не
поддерживается», они относятся к N/A; в text/md списки усечены до 12 имён с «+K», в JSON — полные списки),
замечания (нераспознанные или отброшенные строки, обрезанная последняя строка, неполный последний снимок, в том
числе без строк TOP, неизвестные секции, AIX-секции, смена заголовков секций между запусками nmon в файле, снимки
без ZZZZ — WARN, если время всех снимков файла оценено по interval:
реальные моменты неизвестны, сопоставление с логами приблизительно, разрывы и заморозки не видны; WARN, если
время части снимков определить нельзя и они не использованы; CRIT — только если у хоста нет ни одного снимка с
реальным временем и снимков меньше 3; план снимков vs факт, дрожание шага > 25 %, движение времени назад между
соседними строками ZZZZ в порядке файла — снимки при этом переупорядочиваются по времени, а снимки, чья метка
совпала с более ранним снимком того же файла, отбрасываются (WARN с их числом); разрывы — с пометкой «между
файлами/запусками nmon: nmon не работал» или «заморозка хоста / остановка nmon»; INFO о каждом первом снимке
файла/запуска, который есть в выборке (время, `Tnnnn`, файл), а при `--skip-first` — «первые снимки исключены»
(если кроме первых снимков в выборке ничего нет, сверки VM ↔ DISK — «мало данных», на вердикт не влияют);
перезагрузка
ОС между файлами или запусками nmon — boottime различается больше чем на 2 мин; смена OS, cpus или MemTotal
между ними; больше 10 % снимков файла отброшено как дубликаты — WARN с подсказкой про `--no-merge`, а если
отпечаток машины совпадает (копия того же файла) — INFO; объединение файлов
отключено из-за разных машин; CRIT — отсортированный файл с несколькими запусками nmon) и **вердикт**: пригодны
/ с оговорками / непригодны. Замечания — таблица «severity, замечание» (попадает в `csv` и `json`); `--no-info` и
`--min-severity` скрывают часть строк, вердикт считается по всем. Каждая проваленная перекрёстная проверка,
влияющая на вердикт, дублируется в замечаниях строкой `WARN  перекрёстная проверка не пройдена: <проверка> =
<значение>` — причина «с оговорками» всегда видна в замечаниях (в любом формате вывода).

Сверка page faults TOP с VM не влияет на вердикт (в колонке ok расхождение помечается «нет (инфо)»). Если Σ TOP
MajorFault в десятки тысяч раз больше `VM pgmajfault`, но `(Minor + Major)` или `(Minor + 2·Major)` процессов
TOP сходится с `VM pgfault` (0.85–1.1), это не ошибка данных: MajorFault процесса учитывает и faults, завершённые
после повтора (ожидание страницы под чтением/записью, блокировки), а не только чтения с диска; check пишет
«MajorFault в TOP включает faults, завершённые после повтора (не чтения с диска); согласуется с pgfault». Строка
сверки с pgfault — «да», только если одно из двух отношений в 0.85–1.1, иначе «нет (инфо)». Если сверка с pgfault
не сходится, выдаётся INFO «колонка TOP MajorFault в этом файле ненадёжна; для major faults используйте
vm.pgmajfault». Если сверить не с чем — колонки `VM pgfault` нет или она всегда 0, — строки сверки с pgfault нет, а
INFO говорит, что смысл колонки MajorFault не установлен (о чтениях с диска судите по `vm.pgmajfault`); `at`
помечает такую колонку `(TOP, не сверено)`. Сверка выполняется и при `VM pgmajfault = 0` (отношение = ∞).

### `report` — сводный отчёт по хосту
**Ключевые показатели** (период, CPU/RAM, ОС, CPU busy avg/p95/max с временем, user/sys/wait/steal, макс. ядро
без первых снимков файлов, Runnable/Blocked, память used/avail (с калибровкой по MemAvailable)/page cache без
shmem/swap, swap-out, major faults, активность kswapd (pageoutrun), счётчики direct reclaim/kswapd_steal — с
пометкой `n/a`, если ядро их не отдаёт, диски (busy,
пики записи и чтения — без первых снимков файлов, как в `disk`; для диска без своей ФС в скобках — точки
монтирования его LV/разделов), сеть, ФС ≥ 70 % (без псевдо-ФС, см. `fs`), основные JVM (CPU, RSS, потоки;
«исчез из TOP после <время>», если до конца данных — по полному ряду, а не по окну — есть снимки TOP без него, и
новый PID при перезапуске; нет основных — до 3 java с наибольшим CPU; остальные java — одной строкой «прочие java»
с числом PID), процессы по суммарному CPU (группы команд, как в `top --by-cmd`; `<группа> Σ/снимков X% (avg когда
виден Y%, max Z%, N сн.)` — X = Σ %CPU / число снимков с TOP, как `cpu Σ/снимков%` в `top`, по нему сортировка;
Y — среднее только по снимкам присутствия));
**Замечания (health)**; **Таймлайн** с шагом 5/15/60 мин в зависимости от длины периода (для стресс-метрик
`cpu.wait`, `proc.runq`, `proc.blocked`, `disk.busy_max` — max в корзине, чтобы не терять пики; для активности —
`cpu.busy`, `disk.*`, `net.*`, `top.java.cpu` — и памяти — среднее снимков корзины: max скрыл бы провал записи,
трафика или CPU java — сигнатуру остановки операций; короткие пики активности — `timeline --agg max`, `events`;
avail — `mem.avail_cal`; заголовки колонок с единицами, как в `timeline`; границы корзин кратны шагу от полуночи). Статистики рядов
(avg/p95/max и время максимума, min avail, таймлайн) считаются без первого снимка каждого файла и запуска nmon
(T0001 охватывает 1–2 с на старте — ложные max); период, число снимков и суммы «за период» (swap out, reclaim) — по
всем снимкам. Если в выборке (узкое окно, файл из одного снимка) нет ничего, кроме первых снимков файлов, вместо
статистик рядов — строка «статистика рядов: недоступна: T0001 не исключён …», а `health` выдаёт INFO
`NMON_FIRST_ONLY` и правила по рядам не применяет. Секция MEM не Linux-формата (AIX) — строка «память: …» вместо
показателей памяти. Начинайте анализ хоста с этой команды.

### `health` — только замечания
Итог по числу CRIT/WARN/INFO и список замечаний в формате:

```
[CRIT] DISK_BUSY @ 2026-03-14 03:00:08: busy p95 nvme0n1 (/opt/ignite/db) = 98.7 (порог ≥ 80.0)
    факты: avg 47%, max 100% @ 2026-03-14 03:00:08; write max 177505 KB/s, read max 165081 KB/s
    подсказка: диск загружен: checkpoint/WAL/rebalance/снапшот; ...
```

Коды и пороги — раздел 6. Код возврата: 2 при CRIT, 1 при WARN, 0 иначе — по всем замечаниям, независимо от
`--no-info`/`--min-severity` (они меняют только вывод; итог CRIT/WARN/INFO тоже считается по всем); 3 — ошибка
данных или аргументов.

### `cpu` — загрузка процессора
Сводка CPU_ALL (avg/median/p95/max с временем/min для busy, user, sys, wait, idle, steal; у постоянного ряда,
например steal = 0, «время max» = `-`); время выше порогов busy 50/70/80/90/95 % и wait 5/10/25 %; топ пиков
busy с разложением и топ-процессом снимка; эпизоды насыщения (busy > WARN `CPU_SATURATION`, по умолчанию 80 %, ≥ 2
снимка подряд) и эпизоды iowait > WARN `CPU_WAIT` (10 %) — те же пороги (с учётом `--thr`), что у `events`
(«Эпизоды превышения порогов») и `CPU_SATURATION_RUN`; блок **Ядра**: число ядер (`N (с данными M)` и список ядер без данных, если у части ядер нет значений —
offline/hotplug, файлы с разным числом CPU), CV средних по ядрам, «максимальное ядро» avg/p95/max с временем,
число снимков с ядром > 90 % и, отдельно, с ядром > 90 % при общей загрузке < 50 % (однопоточное узкое место) с
числом эпизодов; **эпизоды горячего ядра** (ядро > 90 % при общем busy < 50 % ≥ 2 снимка подряд, самые длинные
первыми: начало, конец, длительность, ядро — самое частое в эпизоде и число разных ядер (поток может мигрировать,
эпизод при этом не рвётся), max/user/sys горячего ядра в точке максимума, средний общий busy, топ-процесс); самые
загруженные ядра (сортировка по времени > 90 %, затем p95); ядра с наибольшим iowait; busy в «ядрах». **Все
статистики — без первого снимка каждого файла** (T0001 охватывает неполный интервал: завышенные busy/wait и ложные
100 % на одном ядре). Длительность эпизода — по меткам времени + интервал (короткие пропуски снимков внутри
входят в неё); на пропуске данных > 5 интервалов эпизод разрывается.

Интерпретация: `busy` = User + Sys (steal не входит). nmon для Linux включает в Sys% время system + irq +
softirq: сетевой трафик повышает sys, а CPU, обслуживающие прерывания/softirq сетевых карт (IRQ affinity,
RSS/RPS), выглядят загруженнее по sys (горячее ядро с sys ≫ user — обработка прерываний, с user — поток
приложения). На узле с 64 CPU общая загрузка 15 % может скрывать одно ядро на 100 % — это видно только в блоке
«Ядра» и в эпизодах горячего ядра. `wait` (iowait) — CPU простаивал, пока были незавершённые операции
ввода-вывода; при высокой загрузке CPU iowait занижается. `steal` > 0 бывает только в виртуальных машинах и
означает, что гипервизор отбирает время.

### `cores` — таблица по каждому логическому CPU
Опции: `--sort avg|p95|max|sys|wait`, `--top N`. Колонки: avg/p95/max busy, avg user/sys/wait, max steal, время > 90 %.
Дополнительно: топология из lscpu (списки CPU всех NUMA-узлов), почти неиспользуемые ядра (avg < 1 %, признак
cpuset/isolcpus/IRQ-only), загрузка по NUMA-узлам (если узлов > 1; avg/p95/max busy и avg sys% ядер узла),
физические ядра по /proc/cpuinfo и сколько физических ядер имели оба HT-потока > 80 % одновременно. Все блоки —
без первого снимка каждого файла, как и в `cpu`. Нумерация nmon `CPU001` = CPU 0 в ОС.
Если в BBBP есть `/proc/stat` (Linux): **прерывания с загрузки ОС** — irq и softirq в % времени всех CPU, доля
irq+softirq в system+irq+softirq (сколько sys nmon приходится на прерывания), доля softirq на 25 % CPU с наибольшим
softirq, и таблица CPU с наибольшей долей softirq (softirq/irq/system/user/iowait в % времени этого CPU). Это
средние **с загрузки ОС до старта nmon**, а не за период записи; если на четверть CPU приходится > 75 % softirq,
печатается «Концентрация прерываний» со списком CPU, набирающих 75 % softirq (обработка сетевых прерываний
сосредоточена на части ядер: IRQ affinity, RSS/RPS). Без `/proc/stat` в BBBP или без полей irq/softirq (старые
nmon и ядра, AIX) блоки не выводятся.

### `proc` — планировщик
Runnable (очередь на выполнение, мгновенное значение в момент снимка), Blocked (процессы/потоки в D-state,
ждут ввода-вывода), pswitch/s, fork/s; время, когда Runnable > 1×CPU и > 2×CPU, Blocked > 1/5/20; **пики
Runnable** (Runnable, Runnable/CPU, busy %, sys %, pswitch, топ-процесс); пики Blocked с iowait, самым занятым
диском и топ-процессом; **Контекст**: pswitch avg/p95 на CPU, корреляции Пирсона Sys% ↔ pswitch (≈ 1 — доля sys
объясняется переключениями контекста: много потоков, futex/epoll, сетевой обмен) и Runnable ↔ busy, переключения
контекста и fork в секунду **с загрузки ОС** (BBBP `/proc/stat` ctxt/processes ÷ uptime — для сравнения с окном
записи), load average 1/5/15 мин на старте nmon (BBBP uptime; десятичная точка или запятая) с отношением к числу
CPU и Runnable + Blocked первых двух снимков (в Linux LA учитывает и процессы в D-state; LA 1 мин > 5 мин >
15 мин — нагрузка росла к моменту старта; LA заметно выше Runnable + Blocked первых снимков — всплеск был до
начала записи). Строки без данных в BBBP не выводятся. Все статистики — без первого снимка каждого файла (в
T0001 pswitch/fork = 0). Колонки syscall/read/write/exec/sem/msg на Linux всегда −1 (nmon их не собирает) и
скрываются.

### `mem` — память
Сводка MEM (начало/avg/min с временем/max с временем/конец/% от total) для memfree, cached, buffers, used,
avail, **avail с калибровкой по MemAvailable (≈ ядро)** (если поправка известна), active, inactive, memshared,
swap used, swapcached (у постоянного ряда, например swap used = 0, «время min/max» = `-`); в примечании —
MemAvailable на старте, оценка avail в опорном снимке рядом с BBBP и величина поправки в MB и % RAM (или причина,
почему её нет, в том числе «нет MemAvailable в BBBP»); тренды (наклон MB/ч, r², «конец − начало» — разница
последнего и первого значений, время до исчерпания — только при r² ≥ 0.7, как в `MEM_GROWTH`); момент минимума доступной памяти с
контекстом (avail и avail с калибровкой, reclaim-счётчики — `allocstall` при нулях за период на ядре ≥ 4.10
печатается `n/a`, топ-процесс); память вне видимых процессов (used − Σ RSS из TOP, плюс Σ ShdLib; если в TOP нет
колонки ResSet — «нет данных», а не вся used как память ядра);
/proc/meminfo на старте nmon и `Committed_AS − AnonPages − Shmem` — верхняя оценка обещанной процессам, но ещё
не занятой памяти (heap, data regions, стеки потоков, арены malloc), с долей от MemAvailable: если она сопоставима
с MemAvailable или больше, при заполнении уже выделенной памяти page cache будет вытесняться, растёт риск
reclaim/OOM (границу выделения при `vm.overcommit_memory=2` проверяет правило `COMMIT_LIMIT`).
Все ряды (сводка, тренды, момент минимума) — **без первого снимка каждого файла и запуска nmon** (T0001), как в
`report`, `health` (`MEM_*`, `SWAP_USED`) и `cluster` (`mem.avail_cal:min`): минимум avail и memfree один во всех
командах; MemAvailable ядра на старте (BBBP) по-прежнему виден в примечании сводки.
В JSON значения таблиц и kv-блоков — числа (MB; для meminfo — KB); в text/md они печатаются в удобных единицах.

Определения: `used = memtotal − memfree − cached − buffers` (как `used` у `free`); `avail ≈ memfree + buffers +
(cached − memshared) + slab reclaimable` — приближение MemAvailable (в nmon MemAvailable нет; `memshared` =
Shmem/tmpfs входит в `cached`, но не вытесняется, поэтому вычитается). Неполный снимок (оборванная строка MEM —
пустые cached/buffers/memshared при колонке, которая есть в файле) даёт пустое значение used/avail, а не ложный
провал; нет строки VM в снимке — slab берётся из предыдущего снимка того же файла; значения вне [0, memtotal]
отбрасываются. Точное MemAvailable ядра на момент старта есть в блоке meminfo и служит для калибровки: оценка выше
MemAvailable примерно на постоянную величину в MB — резервы ядра (totalreserve_pages, low watermark, часть
slab): обычно доли процента RAM при настройках по умолчанию и несколько процентов при увеличенных
`vm.min_free_kbytes` / `vm.watermark_scale_factor`; в процентах от avail разница тем больше, чем меньше avail.
Поправка (оценка − MemAvailable) считается один раз по опорному снимку — первому снимку файла, из которого взят
BBBP (если он пуст или вытеснен дедупликацией — ближайшему снимку того же файла в пределах 2 интервалов, а если
вытеснены все снимки этого файла — снимку другого файла хоста в тот же момент, ±0.5 интервала: файлы разных машин
не объединяются), и не меняется при `--from/--to/--around/--skip-first`. r² близко к 1 при положительном наклоне =
устойчивый рост (утечка/накопление); низкое r² = колебания. Отрицательное «used − Σ RSS» — норма, когда в RSS
процесса много file/shmem-страниц (колонка ShdLib), которые nmon учитывает в `cached`, а не в `used`.

### `vm` — подкачка, reclaim, page faults, грязные страницы
Сводка по счётчикам VM: pgpgin/pgpgout (KB/s), pswpin/pswpout (страниц за интервал), pgfault/pgmajfault (/s),
kswapd_steal, pgscan_kswapd, pgscan_direct, pgsteal, allocstall, pageoutrun, slabs_scanned, pgdeactivate,
pgactivate (за интервал), nr_dirty/nr_writeback/nr_mapped/nr_slab/nr_page_table (MB, текущие значения); блок
грязных страниц (max dirty, время сброса при средней скорости записи, nr_writeback); признаки давления на
память (swap-активность, reclaim, `kswapd* в TOP` — сумма по всем kswapdN: число снимков, CPU avg по снимкам,
где kswapd виден, и max; справочно — по каждому kswapdN, обычно один на NUMA-узел); замечание о «мёртвых»
счётчиках ядра. Значения /s считаются по фактическому шагу между соседними снимками одного файла и запуска nmon
(после разрыва — среднее за весь разрыв, а не завышенное в разы); «за интервал» — приращение с предыдущего
снимка, после разрыва оно покрывает весь разрыв. avg/p95/max, «время max» (у постоянного ряда — `-`), «снимков > 0» и
блок грязных страниц — **без первого снимка каждого файла и запуска** (T0001: приращение за 1–2 с), как в `report`
(«kswapd активен … из N») и `health` (`KSWAPD_ACTIVE`, `MAJFAULT_HIGH`); «сумма за период» — по всем снимкам
(приращение T0001 — реальные события), число снимков обоих рядов — в примечании.

**Важно:** на современных ядрах Linux колонки `kswapd_steal`, `pgsteal_*` (переименованы с ядра 3.4),
`pgscan_kswapd_*`, `pgscan_direct_*`, `pgrefill_*` (с 4.8), `allocstall` (с 4.10) в nmon **всегда 0**: имена
счётчиков в `/proc/vmstat` изменились, nmon читает старые. На RHEL/CentOS 7 (ядро 3.10) `allocstall` и
`pgscan_*_normal` ещё работают; на RHEL 8/9 и производных, Ubuntu 18+ — нет. Не делайте из их нулей вывод
«reclaim не было». Признаки reclaim на современных ядрах: `pageoutrun > 0` (kswapd просыпался),
`slabs_scanned > 0`, рост `pgdeactivate`, процессы `kswapd*` в TOP с заметным CPU, memfree у нижней границы.
Прямой reclaim (allocstall) на ядрах ≥ 4.10 в nmon не виден вообще — `health` дописывает это к «признаков
давления нет» в `MEM_FREE_LOW` и `KSWAPD_ACTIVE`.

### `disk` — блочные устройства
Опции: `--dev REGEX` (полное совпадение по имени устройства или имени LV, можно несколько), `--all`
(включая разделы и dm-*), `--top N`. По умолчанию показываются **физические** устройства (без разделов и
dm-*, чтобы не считать трафик дважды: запись в LV проходит и через dm-N, и через физический диск).

Вся статистика команды (таблица, итоги, объёмы, svc≈ms, распределение по LV, пики, время обслуживания) считается
**без первого снимка каждого файла/запуска** (T0001 охватывает 1–2 с старта nmon, когда его же команды BBBP
читают диск: ложные max и «время max» на старте). Так же считаются дисковые правила health (раздел 6) и строка
«диски» в `report`; `--skip-first` для `disk` не нужен.

Таблица: устройство (для dm-N в скобках имя LV), mount (для физического диска без своей ФС — точки монтирования
его LV/разделов), busy avg/p95/max с временем, время > 80 %, read/write avg/max KB/s, IOPS avg/max, средний размер
IO (KB, = Σ(read+write)/Σ IOPS — взвешенно по операциям, простои не занижают), `svc≈ms` (оценка времени на
операцию = util×10/IOPS, медиана по снимкам с IOPS ≥ 10) и `svc n` (число таких снимков; при `svc n` < 5
оценка не выводится — `-`), `stalled` (снимков с busy ≥ 95 % при IOPS < 1 — устройство «висит»),
прочитано/записано всего (Σ скоростей × фактический шаг снимка: после разрыва — его длительность, как в `export
--agg sum`; один интегратор для объёмов `disk`, `net`, NETERROR и сверок `check`). «Время max» у постоянного ряда
(busy = 0) — `-`. **svc≈ms — не await**: для NVMe и устройств с параллельной
очередью util×10/IOPS занижает время операции в разы (несколько операций обслуживаются одновременно, util считает
время, а не очередь); для HDD/SAS сверяйте с `avg read/write ms` из `diskmap` (/proc/diskstats, с загрузки ОС).
Итого по физическим дискам — отдельными числовыми ключами (read/write avg и max KB/s, IOPS avg/max, прочитано и
записано за период в KB, доля записи %). **Распределение трафика по LV/разделам** (только без `--all`/`--dev`, если
есть lsblk и у физического диска ≥ 2 смонтированных потомков): какой LV/раздел даёт чтение и запись диска — read/write
avg KB/s, доля от трафика диска, busy p95; строки с долей < 1 % в обоих направлениях скрыты, LV/RAID/multipath поверх
нескольких дисков не показываются. Пики записи и чтения по каждому устройству с busy, размером IO и топ-процессом —
только значимые (> 0, ≥ p90 ряда и ≥ 10 % максимума; у разреженного ряда их может быть меньше `--top`, тогда в
примечании «значимых пиков: k»); **периодичность
всплесков**: интервалы между локальными пиками ≥ p90 — период считается установленным («всплески регулярны»),
только если интервалов ≥ 8, период ≥ 3 шагов nmon и ≥ 60 % интервалов лежат в пределах max(±25 %, ±1 шаг) от
медианы (фактический допуск печатается в секундах); иначе печатается «пики нерегулярны» с медианным
интервалом и разбросом; если выраженных пиков для оценки мало (p90 ряда ≤ 1.2 × медианы, меньше 3 локальных пиков ≥
p90 или меньше 2 интервалов ≥ 60 с между ними) — «периодичность не оценена». Регулярный период ≈ 180 с — типичная сигнатура checkpoint Ignite (`checkpointFrequency`
по умолчанию 180 с), но при интервале nmon 60 с трёхминутный цикл находится на пределе разрешения: для
уверенной детекции нужен интервал ≤ 30 с. Таблица времени обслуживания — если в файле есть
DISKREADSERV/DISKWRITESERV. `--dev` сопоставляется с именем устройства (`dm-4`), с именем из /dev/mapper
(`vg-lv`, как в колонке LV команды `diskmap`) и с именем LV без группы томов (`lv`). В JSON все значения —
числа (объёмы в KB, «время > 80 %» в секундах — см. поле `units`).

Интерпретация busy: доля времени, когда у устройства была хотя бы одна операция в очереди (util). Для HDD/SAS
busy ≈ 100 % — реальный предел; для NVMe и RAID с параллелизмом 100 % достигается задолго до предела
пропускной способности, поэтому смотрите ещё IOPS, размер IO, Blocked и iowait. Маленький средний IO (4–8 KB)
при высоком busy = случайные/синхронные записи (WAL fsync, страницы checkpoint); большой (≥ 64 KB) =
последовательные (архив WAL, снапшот, бэкап).

### `diskmap` — карта хранилища
Устройство nmon → тип → размер → **физический диск** (корень дерева lsblk) → родитель → LV → точка
монтирования (для диска без своей ФС — точки монтирования потомков) → fs → use % на старте → опции монтирования
(из дерева lsblk, `ls -l /dev/mapper`, /proc/partitions, mount, df -m в BBBP). LV, md-RAID или multipath поверх
нескольких дисков lsblk показывает под каждым из них — в колонках «физ. диск» и «родитель» тогда перечислены
**все** диски/родители через запятую (striped LVM или RAID0 из двух NVMe: `nvme0n1, nvme1n1`). Далее: `df -m` на
старте (псевдо-ФС скрыты, полный вывод — `bbbp --block df-m`); точки монтирования, похожие по именам на хранилище
Ignite (ignite/wal/persist/snapshot/archive/db/data) с указанием всех физических дисков — так видно, делят ли
WAL, persistence и архив один диск; `/proc/diskstats` на
старте — накопительно с загрузки ОС: число операций, средняя латентность ms/операцию (включая очередь),
средний размер IO, объёмы, util с загрузки, in_flight; `/etc/fstab`. По латентности с загрузки легко отличить
HDD/SAS (> 5 ms) от SSD/NVMe (< 1 ms). Используйте эту команду, чтобы понять, какой физический диск стоит за
каталогами persistence/WAL/архива/снапшотов/логов. Размеры и объёмы в JSON — числа (размер устройства и df — MB,
объёмы /proc/diskstats — KB; поле `units`); размер устройства — из /proc/partitions, без него — из lsblk. Имена
`ddev/…` (так nmon пишет `/dev/…` в BBBP) приводятся к `/dev/…` в mount, df и fstab; перенос длинного имени
устройства на отдельную строку (df старых coreutils без `-P`) склеивается.

### `fs` — заполненность файловых систем
Опции: `--mount REGEX` (полное совпадение, например `/opt/ignite.*`, можно несколько; если не совпала ни одна
точка — сообщение «не найдены» со списком доступных). Для каждой точки монтирования (JFSFILE): размер (из df), % в
начале/конце/min/max с временем (у постоянного ряда — `-`), Δ за период, рост п.п./ч и r² (регрессия), рост MB/ч,
время до 100 % при текущем росте (печатается только при r² ≥ 0.7 и росте ≥ 0.05 п.п./ч — то же условие, что у
`FS_GROWTH`, иначе `-`), свободно в конце; JFSINODE, если есть.
**Скачки заполненности** (удаление/ротация/создание снапшота) — по тем же точкам, что в основной таблице: за
интервал ≥ 2 п.п. либо, если размер ФС известен из df, ≥ 0.3 п.п. и ≥ 10 GB (на томе 10 TB 1 п.п. — это
100 GB); колонка `Δ, MB` = Δ п.п. × размер ФС; при > 50 скачках показываются 50 крупнейших по |Δ, MB| (без размера
— по |Δ|), в порядке времени, с «показано N из M». **Псевдо-ФС** скрыты (укажите их явно через `--mount`):
точки `/dev`, `/run`, `/sys`, `/proc` и всё под ними; тип ФС по mount — tmpfs, devtmpfs, squashfs, overlay,
iso9660, udf, ramfs, proc, sysfs, cgroup/cgroup2, devpts, mqueue, hugetlbfs, autofs; либо имя в df — tmpfs,
devtmpfs, overlay, shm. То же правило — в `health` (FS_FULL, FS_GROWTH) и строке `report` «ФС ≥ 70 %».
Разрешение JFSFILE — 0.1 %, на больших ФС один шаг = гигабайты, поэтому оценка роста — линейная экстраполяция.

### `net` — сеть
Опции: `--iface REGEX` (полное совпадение имени, например `bond.*`, можно несколько; фильтрует таблицы
интерфейсов, отрезков молчания, bond с одним активным слейвом, счётчиков и NETERROR; «Итого» и «Пики суммарного
трафика» — всегда по всем основным интерфейсам хоста, о чём сказано в их примечаниях; если не совпал ни один
интерфейс — сообщение «не найдены» со списком доступных), `--all` (показать интерфейсы без трафика и без данных),
`--link-mbit N` (скорость одного порта).

Вся статистика (таблица интерфейсов, «Итого», объёмы, пики, отрезки молчания, NETERROR) — **без первого снимка
каждого файла и запуска nmon** (T0001), как в `report`, `health` (`NET_*`) и `cluster`. Объёмы «за период» —
Σ скорости × фактический шаг снимка (после разрыва — его длительность), как в `disk` и `export --agg sum`.
Интерфейс, у которого в файле есть колонки, но нет ни одного значения, в итог не входит (итог — по остальным
основным интерфейсам) и в таблице скрыт без `--all`.

Роли интерфейсов: `lo` (имя `lo`, `lo0`… или флаг LOOPBACK); `vlan` — `<родитель>.<N>` поверх интерфейса из NET,
если его трафик не больше родительского (иначе `nic`: например, дочерние разделы IPoIB со своими счётчиками);
`virtual` — veth, docker*, br-*, virbr, vnet, tap, tun, cali, flannel, cni, vxlan, weave, cilium, lxc, kube-*;
`bridge` — br<N>, bridge<N>, ovs-* (если есть NIC/bond с трафиком; иначе мост остаётся `nic`); `bond-slave` /
`bond` — по флагам SLAVE/MASTER из ifconfig (новый формат `flags=…<…>`, в том числе шестнадцатеричный, и старый
`Link encap … UP BROADCAST … SLAVE … MTU:`); при нескольких bond слейв относится к bond с тем же MAC, остальные
(balance-tlb/alb) — по совпадению рядов. Если флагов нет (в BBBP нет ifconfig, `team<N>`), слейвы определяются
**по совпадению рядов rx/tx во времени**: подмножество NIC, сумма которых по снимкам ближе всего к рядам bond
(относительная ошибка ≤ 10 %; NIC не может превышать bond) — роль `bond-slave (по трафику)`; если набора нет,
примечание «слейвы bond по трафику не определены», bond и NIC остаются в итоге. Остальные — `nic`.

Блоки: **Интерфейсы** — роль, MTU, rx/tx avg/p95/max KB/s с временем максимума, пакеты/с, средний размер пакета
за период и **в пиках** (`B/pkt в пиках` — по снимкам с трафиком ≥ p95), объёмы за период (в JSON — KB); при
`--link-mbit` — `util p95 %` / `util max %` (максимум из rx и tx: NIC и слейв — относительно одного порта, bond —
порта × число RUNNING-слейвов, bond с одним активным слейвом — одного порта; у VLAN, виртуальных и bond
неизвестного состава — `-`). **Итого** — сумма без lo,
bond-слейвов, VLAN, мостов и виртуальных интерфейсов (их трафик учтён на нижележащем интерфейсе): отдельные числовые
ключи `rx/tx avg|p95|max KB/s`, `принято/передано за период` (в JSON — KB), при `--link-mbit` — максимальная
загрузка порта p95 / max и имя порта (ёмкость переводится в KiB/s, как считает nmon). **Пики суммарного трафика** —
rx/tx KB/s, pkt/s и B/pkt в снимке (Σ KB/s × 1024 / Σ pkt/s основных интерфейсов), sys %, топ-процесс. **Отрезки
нулевого трафика и провалов** (от 2 снимков): «ноль» — rx+tx < 0.5 KB/s у интерфейса с обычным уровнем p75 ≥ 5
KB/s; «провал < 5% p75» — ниже max(0.5 KB/s, 5 % p75) при p75 ≥ 50 KB/s; у слейва bond — ноль или провал, пока
сам bond передаёт ≥ 5 % своего p75 (тип «… с начала записи …» — до отрезка слейв ни разу не нёс трафик: резервный
слейв или линк, поднявшийся позже, а не отказ); p75 считается по всему периоду данных, в том числе при `--from/--to/--around`
(иначе в узком окне вокруг провала он был бы занижен самим провалом); на пропуске данных > 5 интервалов отрезок
рвётся, длительность — по меткам времени + интервал. **Bond с одним активным слейвом** (active-backup или LACP с
одним живым портом): в ≥ 95 % снимков, когда bond передаёт ≥ 5 % своего p75 (таких снимков ≥ 10), один из
слейвов несёт ≥ 95 % rx+tx bond — таблица «активный слейв, с, по»: смена строки — переключение (failover);
молчание второго слейва такого bond — норма и в отрезки молчания не входит. Режим bond определяется по **полному
ряду** хоста (без первых снимков файлов), а не по окну `--from`/`--to`/`--around`: окно, целиком попавшее в отказ
слейва LACP, не выглядит как active-backup — отказ виден в окне так же, как в полном ряду (`NET_BOND_MEMBER`,
обрезанный по окну); отрезки активности обрезаются по окну, признак «молчал с начала записи» тоже считается по
полному ряду до начала отрезка. **Счётчики интерфейсов на старте** (ifconfig, без него — /proc/net/dev;
накопительно с загрузки ОС): роль, packets, errors, dropped, overruns (fifo), frame, carrier, collisions; счётчики
bond = сумма счётчиков слейвов + собственные. **NETERROR** (если есть): ≈ событий за период = Σ rate × шаг снимка,
max /s; у bond с известными слейвами — только остаток сверх одноимённых колонок слейвов.

Как читать: размер пакета ~100–500 B — мелкие сообщения/RPC и подтверждения, ~MTU (при jumbo — несколько KB) —
массовая передача (rebalance, снапшот, putAll). Среднее за период определяется фоном мелких сообщений, поэтому
передачу смотрите в пиках: `B/pkt в пиках`, таблица пиков, метрики `net.tx_size` (у отдающих) / `net.rx_size` (у
принимающих). `--link-mbit` — скорость порта, а не агрегата: при сравнении bond со скоростью агрегата перекос
хеширования LACP скрыл бы насыщение одного порта; средние за интервал nmon скрывают микровсплески — заметная
загрузка по nmon уже допускает кратковременное насыщение порта. «Провал» при остаточном трафике (ssh,
мониторинг, ARP/LACP) — типичная картина изоляции узла, которую порог «ноль» не видит.

### `top` — процессы (секция TOP)
Опции: `--pid N` (несколько раз), `--cmd REGEX`, `--by-cmd` (группы команд, см. ниже),
`--sort cpu|cpuavg|cpumax|rss|threads|majflt|sys|snapshots`, `--top N` (по умолчанию 20). Колонки: команда, pid
(при `--by-cmd` — `PID шт.`, число разных PID группы), снимков (в скольких снимках процесс попал в TOP),
впервые/последний раз, **`cpu Σ/снимков%`** — среднее за весь период (Σ %CPU / число снимков с TOP: снимок без
процесса = 0; ключ `--sort cpu` по умолчанию — так постоянный фоновый потребитель не тонет среди kworker,
мелькнувших в одном-двух снимках с высоким %CPU), `cpu avg% (когда виден)` — среднее только по снимкам
присутствия (`--sort cpuavg`), cpu p95/max с временем, доля sys, RSS начало/max/конец (MB), threads
начало/max/конец, major faults avg/max в секунду, minor faults avg в секунду, сумма IOwaitTime. Имя kworker
содержит текущую задачу workqueue и меняется (`kworker/u64:1-writeback` → `kworker/u64:1-flush-253:0`): в
режиме по PID показывается самое частое имя и `(имён: N)`. `--by-cmd` группирует так: kworker — по задаче
(`kworker/*-writeback`, `kworker/*-flush-*` — номер устройства заменён на `*`, без задачи — `kworker/*`), потоки
ядра по CPU (`ksoftirqd/N`, `migration/N`, `cpuhp/N`, `watchdog/N`, `rcuo*/N`, `idle_inject/N`) — `<имя>/*`
(такие имена групп принимает и `top.<группа>.<поле>`, например `top.kworker/*-writeback.cpu`); значения группы —
**суммы по всем её PID в снимке** (одна строка на снимок; RSS — сумма, разделяемые страницы учитываются
несколько раз). Дополнительно: учёт CPU (сумма %CPU процессов в пересчёте на все CPU vs CPU_ALL busy — busy
берётся по тем же снимкам, где есть TOP, без первого снимка файла; неучтённая доля = мелкие процессы ниже порога
TOP, прерывания, kernel-потоки) и смена PID у команды `java` (перезапуск: PID исчез до конца данных, и после этого
впервые появился новый PID той же команды, не существовавший одновременно со старым; одновременно работающие JVM
перезапуском не считаются; пары подбираются по роли — см. `JAVA_RESTART` в разделе 6: короткая утилита java в окне
простоя не делит перезапуск узла на два; считается по полному ряду, при окне времени показаны перезапуски, простой
которых захватывает окно).

**Порог TOP:** nmon пишет в TOP только процессы, потреблявшие заметный CPU в интервале, и начиная с T0002.
Отсутствие процесса в снимке ≠ он не работал (он мог быть idle). `%CPU` — в процентах **одного** ядра: 640 %
= 6.4 ядра; на 64 CPU это 10 % машины. `MinorFault`/`MajorFault` — события **в секунду** (nmon делит приращение
на длину интервала); `MajorFault` процесса может включать faults, завершённые после повтора (см. `check` и раздел
9). `IOwaitTime` учитывает только главный поток процесса и для многопоточных JVM неинформативен. Если в окне
`--from/--to/--around` нет снимков с TOP, а в файле TOP есть, `top`/`java`/`report` пишут «в выбранном окне нет
снимков с данными TOP … расширьте окно»; «nmon без -t» — только когда TOP нет в самом файле.

### `java` — JVM (Ignite) глазами ОС
Подробный kv-блок `java[<pid>]` — для каждого основного JVM и для `--top N` (по умолчанию 5) вспомогательных java
с наибольшим Σ %CPU; остальные вспомогательные (короткие утилиты и клиенты — их бывают тысячи) — одной таблицей
«Вспомогательные java без подробного блока»: pid, впервые/последний, снимков, cpu Σ/снимков%, cpu max, RSS max,
threads max, роль по UARG; не больше 20 строк по Σ %CPU, в примечании — общее число PID, их период и суммарный
CPU. В блоке каждый показатель — отдельным ключом (в JSON — числа; RSS,
анонимная RSS, ShdLib, VSZ — в MB с `units`, в text — в удобных единицах; неизвестное значение — `-` / `null`):
pid; **роль** (основной JVM / вспомогательный java — см. `JAVA_RESTART` в разделе 6); снимков в TOP, снимков с
TOP всего, доля присутствия, впервые / последний раз (при окне времени, если процесс жил и вне окна, — ещё «в TOP
по полному ряду»), **снимков TOP без процесса до первого появления и после последнего** — по полному ряду, а не
по окну (> 0 после — JVM исчезла до конца данных, см. `JAVA_GONE`, либо сменилась новым PID — `JAVA_RESTART`,
об этом говорит примечание); %CPU avg/p95/max (в % одного ядра),
время максимума, ядер avg/max, % машины avg/max; доля sys в CPU процесса; RSS начало/max/конец (первое и
последнее известное значение) и % от RAM; **анонимная RSS** (ResSet − ShdLib — без file/shmem-страниц, ближе к
реальному потреблению) и её % от RAM; file/shmem-часть RSS; тренд RSS (MB/ч, r²); VSZ; threads
начало/max/конец и тренд (без колонки Threads — «нет данных»); major/minor faults avg/max и faults всего
(minor+major) в секунду; если сверка хоста (`check`) показала, что MajorFault в TOP включает faults после повтора,
— «доля faults после повтора, %» и пояснение «это не чтения с диска; реальные чтения — vm.pgmajfault» (если
сверка не сходится — пометка, что колонка ненадёжна; если сверить с VM pgfault нельзя — колонки нет или она
всегда 0 — пометка «смысл колонки не установлен», без вывода о ненадёжности); IOwaitTime (только главный поток — для JVM
неинформативно); «командная строка (UARG)» — есть / «нет (nmon без -T) — флаги JVM недоступны». Далее: снимки с
CPU < 10 % от медианы (возможные паузы/остановки); пропуски присутствия в TOP («пропущено» — снимков с TOP без
процесса; при окне — паузы, захватывающие окно, по полному ряду); пики %CPU с контекстом (sys,
CPU_ALL, iowait, RSS, threads, majflt/s); перезапуски (смена PID по времени жизни каждого PID с учётом роли,
простой между, RSS нового и старого процесса — маленький RSS нового = «холодный» старт; все смены PID основных JVM и
до 30 строк вспомогательных); другие процессы с
заметным CPU — по группам команд, как `top --by-cmd` (суммы по PID в снимке; сортировка по `cpu Σ/снимков%`),
с категорией (мониторинг, антивирус, бэкап, kernel reclaim, kworker по задаче: «I/O/writeback» — writeback,
flush, задачи ФС и блочного слоя; «служебные очереди» — events*, mm_percpu_wq, rcu*, cgroup*; «прочие workqueue
(драйверы)»; JVM-утилиты…); при наличии UARG (ищется по всему файлу, даже при окне времени) — для PID с подробным
блоком роль JVM, флаги и оценка памяти по флагам (heap + MaxDirectMemorySize + стеки потоков vs RSS → сколько
приходится на off-heap Ignite/metaspace).

Интерпретация: RSS JVM Ignite = heap + off-heap data regions + checkpoint buffer + metaspace + стеки потоков +
буферы + file/shmem-страницы (mmap, tmpfs); рост RSS до суммы настроенных регионов после старта — норма, рост после
плато — повод искать утечку. Высокая доля sys (> 30 %) при заметной нагрузке — page faults (первое касание памяти
без AlwaysPreTouch, запись в mmap-файлы, ожидание страниц под writeback; THP — если AnonHugePages > 0),
futex-конкуренция, сетевой ввод-вывод; у простаивающей JVM (< 0.5 ядра) высокая доля sys нормальна, а если ядро
JVM занимает < 10 % ёмкости всех CPU узла — это профиль нагрузки, а не узкое место (`JAVA_SYS_SHARE` — INFO). GC-паузы nmon
не видит; косвенный признак — провал %CPU при том, что узел не был занят.

### `uarg` — командные строки и флаги JVM (нужен nmon `-T`)
Опции: `--cmd REGEX`, `--full`. Список процессов с командными строками; для java — роль (серверный узел Ignite
по `CommandLineStartup`, ZooKeeper, control.sh, JVM с Ignite в classpath), извлечённые флаги: Xms
(`-Xms`/`-XX:InitialHeapSize`), Xmx (`-Xmx`/`-XX:MaxHeapSize`), Xmn, стек (`-Xss`/`-XX:ThreadStackSize` в KB),
MaxRAMPercentage, MaxDirectMemorySize, MaxMetaspaceSize, тип GC, MaxGCPauseMillis,
ParallelGCThreads/ConcGCThreads, AlwaysPreTouch, UseLargePages, UseTransparentHugePages,
HeapDumpOnOutOfMemoryError, ExitOnOutOfMemoryError, DisableExplicitGC, GC-лог, JMX-порт, все `-DIGNITE_*`, все
`-XX:*` (как есть). Повторённая опция (скрипты запуска ставят `-Xms1g -Xmx1g` по умолчанию, а пользовательские
значения — после) берётся по **последнему** вхождению, как её применяет JVM, с пометкой `64g (переопределяет 1g)`;
main class — по первому. Размеры в байтах или KB (`-XX:MaxHeapSize=68719476736`, `-XX:ThreadStackSize=512`)
дополняются пересчётом: `68719476736 (64.0 GB)`, `512k (512.0 KB)`. Оценка памяти по флагам: heap max (без
`-Xmx`/MaxHeapSize — MaxRAMPercentage × RAM с пометкой «оценка», иначе «по умолчанию 1/4 RAM»),
MaxDirectMemorySize, стеки потоков (threads max × стек, по
умолчанию 1 MB) vs RSS max. nmon пишет командную строку процесса не в каждом снимке, поэтому при окне
`--from/--to/--around` строки UARG ищутся по всему файлу и показываются для процессов, видимых в TOP окна (или
записанных в UARG в окне). Без `-T` секции UARG нет — команда сообщит об этом.

### `at` — срез в момент времени
Опции: `--time T` (форматы и метки логов — раздел 3; по умолчанию — момент максимальной загрузки CPU без первых
снимков файлов/запусков: T0001 охватывает 1–2 с старта nmon, даёт ложный пик и не содержит TOP),
`--window-snaps K` (снимков до/после, по умолчанию 2; `0` — только сам снимок), `--metrics ...` (по умолчанию —
набор `timeline` и `vm.pgmajfault`), `--top N`. Снимок nmon — средние за интервал, **закончившийся** его меткой
времени, поэтому выводится снимок, интервал которого содержит момент (первый снимок со временем ≥ T): его id
`Tnnnn` и «интервал снимка» (`предыдущий снимок .. снимок`; у первого снимка файла/запуска — «неполный
интервал»), а если ближайший по времени снимок другой — и он («ближайший по времени снимок»). Дальше: таблица
ключевых метрик для K снимков вокруг (CPU, диски, сеть, VM, TOP — средние за интервал; Runnable/Blocked, память,
ФС — мгновенные значения на конец интервала), TOP-процессы этого снимка, все устройства с busy ≥ 1 % (включая
разделы и dm-*), сеть (интерфейсы ≥ 1 KB/s с ролью — lo, bond, bond-slave, vlan, bridge, virtual, nic, как в `net`, — pkt/s и средним размером пакета B/pkt;
трафик bond уже включает слейвы — строки не складывайте, итог хоста — `net.read`/`net.write`), ядра с busy > 90 %.
Колонка `majflt/s` TOP помечается «(TOP, вкл. retry)», если `check` относит MajorFault процессов к faults после
повтора, «(TOP, ненадёжно)», если они на порядок расходятся с системным `VM pgmajfault`, и «(TOP, не сверено)»,
если расходятся, а сверить с `VM pgfault` нельзя (колонки нет или она всегда 0), — тогда о чтениях с
диска судите по `vm.pgmajfault` (раздел 9). Строка «ВНИМАНИЕ» (и `WARN` в stderr): момент **в разрыве данных**
внутри периода — с границами и длительностью разрыва (внутри запуска nmon не писал снимки: хост или nmon были
заморожены — сам разрыв улика, значения следующего снимка усреднены за весь разрыв; на границе файлов/запусков —
nmon не работал, а если в разрыв попадает boottime следующего запуска — «перезагрузка ОС» с её временем; снимок
после такого разрыва — начало нового запуска и разрыв не покрывает); момент раньше первого снимка файла/запуска
(nmon ещё не писал: интервал, содержащий момент, не записан — показан первый снимок) и позже последнего снимка
(интервал не записан — показан последний); момент **вне периода данных** (дальше 1.5 интервала до начала или
после конца) — проверьте дату и часовой пояс. Подпись «снимок (интервал содержит момент)» ставится, только если
интервал снимка действительно содержит момент; в остальных случаях — просто «снимок». Это основная команда для
вопроса «что происходило в 03:52 по логу Ignite».

### `timeline` — временной ряд метрик
Опции: `--metrics имена...` (по умолчанию набор из cpu/proc/mem/disk/net/java), `--step 5m` (укрупнение;
границы корзин кратны шагу от фиксированной полуночи: для шагов, делящих сутки, — от полуночи каждого дня, шаг
≥ суток не вырождается в сутки; колонка «снимков» — число снимков в корзине, крайние корзины бывают неполными),
`--agg mean|max|min|sum|last` (агрегат в корзине; для загрузок берите `max`, чтобы не терять пики), `--limit N`.
`--agg sum` даёт количество за корзину (подписи «KB за корзину», «шт. за корзину»): скорости (`KB/s`, `/s`,
`pkt/s`) умножаются на фактический шаг снимка — интервал nmon (у файлов с разным `interval` — свой), после
разрыва — длительность разрыва, как в `vm`; у
первого снимка файла/запуска (T0001) — время от старта nmon (AAA date/time, обычно 1–2 с; `--tz-shift` на это не
влияет); приращения за интервал (`pages/int`, `count/int`) складываются как есть; для уровней (`%`, `MB`,
`count`) сумма бессмысленна — `WARN` (берите mean/max/min/last). `timeline` и `export` агрегируют одним кодом,
примечание таблицы одинаковое. Заголовки колонок содержат единицы. Неизвестные имена метрик пропускаются с предупреждением `WARN:` в stderr (во всех командах с
`--metrics`; `top.<cmd>.*` с процессом, которого нет ни в одном снимке данных, — тоже неизвестная метрика); о
метрике без единого значения (все снимки пусты) — `WARN: … нет значений в данных`, колонка остаётся. Снимки без
данных секции (например, обрезанная строка NET) остаются пустыми (`-`), а не считаются нулём. Удобно с
`--around`/`--from`/`--to` и `--format csv`.

### `events` — выбросы во времени
Опции: `--metrics ...`, `--z 4` (порог робастного z-score; `--z 0` снимает порог по z, но минимальные
абсолютные отклонения по-прежнему отсекают шум), `--window-snaps 15` (окно скользящей медианы), `--limit`
(по умолчанию 200).
Блок «Выбросы»: для каждой метрики выброс = отклонение от медианы соседних снимков более чем на z×MAD и больше
минимального абсолютного порога (cpu.busy ≥ 10 п.п., cpu.core_max ≥ 20 п.п., disk.write ≥ 20 MB/s и т.п.;
по размеру хоста: proc.runq ≥ max(4, CPU/4), proc.blocked ≥ max(3, CPU/16), mem.free/mem.avail/mem.avail_cal ≥
max(1 GB, 1 % RAM), top.java.threads ≥ max(30, 10 % фона), reclaim: vm.pswpin ≥ 1, vm.pgscan_direct ≥ 32,
vm.pgsteal/vm.kswapd_steal/vm.pgscan_kswapd ≥ 1024 страниц за интервал — фактические значения в примечании); для
метрик без такого порога (`cpu.idle`, `raw.*`, `top.<cmd>.*` и т.п.) отклонение должно быть не меньше 5 % фона —
иначе событием становились бы колебания на доли процента — и не меньше минимума по единице метрики: `%` — 5 п.п.
(`top.<cmd>.cpu`/`usr`/`sys` — 10 п.п.), `MB` — 64, `KB/s` — 1000, `/s` и `count` — 1, `pkt/s` — 10, приращения
за интервал — 1 (на нулевом фоне 5 % фона — это 0: без минимума событием стало бы любое появление процесса в TOP).
Провал (значение ниже фона) `net.read`, `net.write`, `disk.read`, `disk.write`, `top.java.cpu` засчитывается уже
при отклонении ≥ min(порога, 50 % фона), если фон не меньше 1 % порога: провал трафика до доли фона (изоляция
узла, остановка нагрузки) виден и на узле с фоном ниже 10 MB/s.
Фон и эпизоды считаются по **полному ряду хоста**, а показываются эпизоды, задевающие окно `--from/--to/--around`,
целиком (как и эпизоды порогов) — узкое окно вокруг инцидента не прячет сам инцидент и не обрезает его
длительность. Первые снимки файлов (T0001) событиями не считаются. Подряд идущие выбросы одной метрики одного знака (промежуток ≤ 1.5 интервала)
объединяются в эпизод: начало, конец, снимков, пик (точка с max |z|), время пика, фон, z. Если эпизодов больше
`--limit`, показываются сильнейшие по |z| (по времени), а не первые: поздние события не теряются. Направление
поиска (одно для `events` и синхронных выбросов `cluster`): для `mem.free`, `mem.avail`, `mem.avail_cal`, `cpu.idle`
(и любых имён на `.idle`) — провалы (z < 0); для нагрузочных `cpu.busy`, `disk.read`, `disk.write`, `net.read`,
`net.write`, `top.java.cpu`, а также `mem.cached`, `top.java.threads` — отклонения в обе стороны (провал записи,
трафика или CPU java — сигнатура остановки операций); для остальных — рост. Знак z совпадает со знаком отклонения; `z = ±99` — плоский фон (MAD и σ окна равны 0, в том
числе нулевой: swap-in, direct reclaim, процесс в TOP с нуля), отклонение при этом не меньше минимального порога. Скользящая медиана видит только всплески **короче примерно
половины окна** (≈ 7 снимков при `--window-snaps 15`): внутри длинного плато медиана сама становится уровнем
плато; длительный провал — например, java десятки минут вне TOP (`top.java.cpu` = 0) — событием не
становится: его показывают `health` (`JAVA_ABSENT`, `JAVA_GONE`) и `timeline`. Устойчивые эпизоды показывает
блок «Эпизоды превышения порогов» — ≥ 2 снимков подряд выше WARN правил health (с учётом `--thr`; те же пороги у
эпизодов `cpu` и эпизодных правил health): cpu.busy > CPU_SATURATION (правило `CPU_SATURATION_RUN`), cpu.wait >
CPU_WAIT, cpu.steal > CPU_STEAL (как эпизоды `cpu`), disk.busy_max > 90 % (`disk.busy_max` — по физическим дискам,
правило `DISK_BUSY_RUN`), proc.blocked ≥ WARN BLOCKED_HIGH (по умолчанию max(5, CPU/8), правило `BLOCKED_RUN`),
proc.runq > RUNQ_HIGH × CPU (`RUNQ_RUN`) — только для метрик из `--metrics`, с длительностью и пиком (эпизоды строятся так же, как у правил `*_RUN`: на пропуске данных > 5
интервалов эпизод разрывается; у мгновенных proc.runq/proc.blocked длительность — промежуток между первым и
последним отсчётом, и эпизод рвёт любой пропуск снимка, как в `RUNQ_RUN`; эпизодов больше `--limit` — остаются
самые длинные, затем с наибольшим пиком над порогом, по времени, с примечанием «показаны N самых длинных из M»);
см. также `cpu`/`disk`/`proc`/`health`. Последний блок — моменты, когда
выбросы случились сразу по ≥ 3 метрикам (наиболее вероятные «события»; по всем выбросам внутри окна, до отбора по `--limit`).
Если в ряду хоста (без первых снимков файлов) меньше 5 снимков, вместо таблицы — сообщение «мало для поиска
выбросов» с числом снимков окна и ряда.

### `correlate` — корреляции Пирсона
Опции: `--metrics ...` (по умолчанию cpu/proc, включая `proc.pswitch`, mem/disk/net/java/vm), `--target M`
(корреляции только с одной метрикой), `--limit`. Считается без первых снимков файлов (T0001). Колонки: `r` —
Пирсон по уровням, `r Δ` — по изменениям от снимка к снимку (первые разности соседних снимков без разрывов),
`n` — общих конечных точек пары, «мало точек» при n < 30 (например, процесс редко попадает в TOP). `r` по уровням
завышается общим суточным трендом нагрузки: метрики нагрузки растут и падают вместе, и многие пары дают
|r| ≥ 0.9 без прямой связи; о связи судите по `r Δ` — он показывает совместные всплески и провалы. Без `--target` — пары с
|r| ≥ 0.5 или |r Δ| ≥ 0.5. Если `--target` постоянна (например, `mem.swap_used` без swap) или почти без данных —
сообщение «корреляция не определена» вместо таблицы. Типичные полезные связи: `disk.write ↔ cpu.wait ↔
proc.blocked` (запись тормозит узел), `net.read ↔ disk.write` (узел принимает данные rebalance/снапшота и пишет
их), `cpu.sys ↔ net.*` (softirq), `cpu.sys ↔ proc.pswitch` (переключения контекста), `vm.pgmajfault ↔ disk.read`
(память вытеснена, читаем с диска). Корреляция ≠ причинность.

### `compare` — два окна времени
Опции: `--a 'HH:MM-HH:MM'`, `--b 'HH:MM-HH:MM'` (или `'начало..конец'` в любом формате времени раздела 3),
`--metrics`, `--top`. Начало окна разрешается как `--from` (одна дата для всех хостов); конец без даты берётся на
дату начала (`'2026-03-14 01:00..02:00'`), а если он раньше начала и данные продолжаются в следующие сутки — на
следующий день (`23:50-00:20`); конец только датой — до конца дня; конец раньше начала — `ERROR`. Без `--a` или
`--b` — `ERROR: compare: укажите оба окна` (код 3); окно, в котором нет снимков ни у одного хоста, — `ERROR` с окном
и периодами данных, только у части хостов — `WARN` (их отчёт — «в одном из окон нет снимков»). Снимки окон
берутся **без первого снимка каждого файла и запуска nmon** (T0001, неполный интервал), как в остальной статистике
рядов: окно у старта nmon не даёт ложных max и сдвинутых средних. Таблица
avg/p95/max в A и B, `Δ abs` = B avg − A avg и Δ % = (B − A) / |A|; при A avg = 0 Δavg % не определён, а в колонке
«рост с нуля» — `yes` (JSON: `true`). Порядок строк: сначала изменения не меньше практического порога (½
минимального отклонения `events`: 5 п.п. для cpu.busy, 2.5 п.п. для cpu.wait, 5 MB/s для net.*; для метрик без
него — 2.5 % от A), затем по симметричному относительному изменению 200·|B − A| / (|A| + |B|) — рост с нуля
(Blocked 0 → 40) наверху, шум около нуля (wait 0.1 → 0.4 %) внизу. Плюс процессы с изменившимся средним
CPU (среднее по всем снимкам окна: отсутствие процесса в TOP считается как 0 %; рядом — в скольких снимках он
попал в TOP). Типовое использование: окно «до инцидента» против окна «во время».

### `cluster` — сравнение хостов
Опции: `--sort метрика:агрегат` (только колонки таблицы, например `cpu.busy:p95`, `net.write:mean`; неизвестная
колонка — ошибка со списком допустимых), `--metrics` (для поиска синхронных выбросов), `--z`. Блоки:
- **покрытие данными** (начало/конец/длительность/снимки/CPU/RAM/разрывы/файлы; в JSON/CSV длительность — секунды,
  RAM — MB, единицы в `units`), объединённое и общее окно, полоса покрытия по времени (`#` — есть данные) — по
  всем снимкам;
- **различия конфигурации** (CPU, RAM, ядро, версия nmon, interval, MTU, swap, THP — используется ли
  (AnonHugePages на старте > 0), а не объём, флаги JVM, модель CPU);
- **метрики по хостам**: mean/p95/max/min за период каждого хоста (в пределах `--from`/`--to`), в том числе
  `net.*:mean` (объём трафика) и `net.*:max` (пик), `mem.avail_cal:min` (avail с калибровкой по MemAvailable, как
  в `MEM_AVAIL_LOW`). Здесь и далее (выбросы, синхронные выбросы, кластерный таймлайн) ряды берутся **без первого
  снимка каждого файла и запуска nmon** (T0001 охватывает 1–2 с на старте: скорости диска за этот отрезок дают
  ложные max). У хоста, для которого в выборке нет ничего, кроме первых снимков файлов (узкое окно у начала
  данных), строка метрик пустая (`-`), в примечании — список таких хостов и «T0001 не исключён …», в кластерный
  таймлайн он не входит (как `report`, который для такой выборки статистику рядов не выводит);
- **выбросы** (только при ≥ 4 хостах): робастный z по медиане/MAD — масштаб 1.4826·MAD, при MAD = 0 — по
  среднему абсолютному отклонению от медианы, и не меньше 5 % медианы (почти одинаковые хосты не дают огромный
  z). Отклонение значимо, если оно ≥ 10 % медианы и не меньше минимального абсолютного (cpu.* и `disk.busy_max` —
  2 п.п., proc.* — 1, mem.* — 100 MB, disk.*/net.* — 1000 KB/s или /s, `top.java.cpu`/`sys` — 50 %, `top.java.rss`
  — 1000 MB, `top.java.threads` — 20). WARN — |z| ≥ 3, CRIT — |z| ≥ 5 **и** отличие ≥ 50 % медианы **и** не
  меньше минимального абсолютного для CRIT (cpu.* — 5 п.п., `disk.busy_max` — 10 п.п., proc.* — 5, mem.* — 1024 MB,
  disk.*/net.* — 10000 KB/s или /s, `top.java.cpu`/`sys` — 200 %, `top.java.rss` — 4096 MB, `top.java.threads` —
  100): при медиане около 0 и MAD = 0 z огромен уже при небольшом отклонении (steal 2.5 % у одного хоста из 8 —
  WARN, а не CRIT); в фактах — «выше/ниже медианы на X %». У метрик, для которых есть правило health
  (`cpu.busy` — `CPU_SATURATION`, `cpu.wait` — `CPU_WAIT`, `cpu.steal` — `CPU_STEAL`, `proc.runq` — `RUNQ_HIGH` × CPU,
  `proc.blocked` — WARN `BLOCKED_HIGH`, `mem.avail_cal` — `MEM_AVAIL_LOW`, `mem.swap_used` — `SWAP_USED`,
  `top.java.rss` — `JAVA_RSS` (оба — в % RAM), `disk.busy_max` — `DISK_BUSY`, `top.java.threads` — `JAVA_THREADS`),
  выброс получает WARN/CRIT, только если он на плохой стороне (выше медианы; у `mem.avail_cal` — ниже) и достигает
  50 % WARN-порога правила (у `mem.avail_cal` — не выше 2 × порога: ≤ 20 % RAM); иначе — INFO «неоднородность
  нагрузки в пределах здоровых уровней» (колонка «уровень» таблицы). Замечание `CLUSTER_OUTLIER` — **одно на хост**:
  метрика и значение — самого серьёзного выброса, в фактах — все выбросы хоста с уровнями (в JSON — массив
  `components`). Хосты, у которых меньше 10 снимков (без первых снимков
  файлов), в сравнении не участвуют (о них — примечание); если таких хостов столько, что сравнивать остаётся меньше
  4, выбросы не считаются — текст «периоды хостов слишком короткие, сравнение хостов не выполняется». Агрегаты для
  выбросов всегда считаются в **общем окне** остальных хостов по рядам без первых снимков файлов (оно может
  начинаться на интервал позже «общего окна» блока «Окна», которое считается по всем снимкам; иначе max/min
  хоста, начавшего запись раньше, приходились бы на время, когда у остальных данных нет), если у каждого хоста в
  нём не меньше max(10, 10 % его снимков); иначе — по полному периоду, о чём сказано в примечании («периоды
  несопоставимы»): тогда агрегаты `:max`/`:min` не сравниваются, а замечания — не выше WARN. Метрика показывается
  как «узлы делятся на группы» (в JSON колонка «хосты» — массив имён), только если отклоняется ≥ max(2, 25 %)
  хостов, все в одну сторону от медианы, и разброс их значений меньше половины их расстояния до медианы (значения
  действительно образуют вторую группу); иначе каждый — отдельный выброс;
- **синхронные выбросы** — эпизоды, когда у нескольких хостов одновременно всплеск или плато (`метрика↑`) или провал
  (`метрика↓`). Направление поиска — как в `events`: обе стороны для `cpu.busy`, `disk.write`, `disk.read`,
  `net.read`, `net.write`, `top.java.cpu`; для `cpu.wait`, `proc.blocked`, `disk.busy_max` — только рост; для метрик
  из `--metrics` — как в `events`. **Кандидаты** у каждого хоста — выбросы как в `events` (`--z`, центрированное
  окно 15 снимков, те же минимальные отклонения под размер хоста; для провалов net/disk/`top.java.cpu` —
  min(порога, 50 % фона)) и, вдобавок, **плато**: центрированное окно не видит эпизоды длиннее ≈ 7 снимков (внутри
  плато медиана сама становится уровнем), поэтому начало сдвига уровня ищется и по «хвостовому» фону — медиане
  15 предыдущих снимков, не входящих в уже найденные эпизоды, с тем же z и минимальными отклонениями; эпизод
  продолжается, пока значение отклонено от фона начала хотя бы на половину начального отклонения (не дольше
  60 снимков — затем новый уровень становится фоном). Всё — по **полному ряду** хоста: при
  `--from`/`--to`/`--around` показываются эпизоды внутри окна, но фон окном не обрезается. Интервал здесь —
  медианный интервал nmon хостов (при `interval` 30 с окно совпадения — 45 с, а не 90). Кандидаты разных хостов
  совпадают, если попали в окно 1.5 интервала nmon от первого (допуск на разную фазу снимков); окно проходит, если
  в нём ≥ max(3, ⌈20 % N⌉) хостов (при 2 хостах в наборе — оба) и их доля среди хостов, у которых рядом есть
  значения метрики, ≥ порога WARN `CLUSTER_SYNC` (50 %); подряд идущие окна (промежуток ≤ 1 интервала) — один
  эпизод. **Участники** эпизода считаются прямо, а не по тому, прошёл ли z-тест отдельный снимок: для каждого хоста
  с данными берётся среднее его снимков, интервал которых больше чем наполовину внутри эпизода (время снимка в
  [начало − ½ интервала, конец + ½ интервала]), против фона — медианы 15 снимков до эпизода вне найденных
  выбросов/плато; участник — при ×≥ 1.25 (↑, и не меньше минимального отклонения) или ×≤ 0.8 (↓). Эпизод
  остаётся, если участников ≥ max(3, ⌈20 % N⌉) и их доля среди хостов с данными ≥ 50 %. Колонки: начало, конец,
  длительность (с начала интервала первого снимка), тип (всплеск / провал / плато — длиннее 7 интервалов), уровень
  компонента, хостов и % хостов (участники), `×значение/фон`, фон и «в эпизоде» (медианы по участникам, в единицах
  метрики), объём, GB (для net/disk: Σ по всем хостам с данными (значение − фон) × длительность снимка; < 0 —
  ниже фона), первый хост, участники. **Уровень** зависит от класса компонента:
  - рост нагрузки (`cpu.busy`, `disk.*`, `net.*`, `top.java.cpu` ↑) — синхронная распределённая нагрузка: INFO;
    WARN — если у ≥ половины участников в окне эпизода есть стресс выше WARN правил health (`cpu.wait` > `CPU_WAIT`,
    `proc.blocked` ≥ WARN `BLOCKED_HIGH`, `disk.busy_max` > 90 %, `proc.runq` > `RUNQ_HIGH` × CPU, при `--link-mbit`
    — загрузка порта ≥ WARN `NET_LINK_UTIL`) или в том же событии есть провал активности; CRIT по одной доле хостов
    не выдаётся;
  - провал активности (те же метрики ↓) — WARN при ×≤ 0.5, доле участников ≥ CRIT-порога `CLUSTER_SYNC` (80 %) и
    длительности ≥ 2 интервалов; CRIT — если вдобавок ×≤ 0.2, или ≥ 5 интервалов, или стресс у ≥ половины
    участников; слабее — INFO;
  - рост стресс-метрик (`cpu.wait`, `proc.blocked`, `disk.busy_max`, `proc.runq`) — только если пик выше WARN
    правила health у ≥ половины участников (иначе «-», только строка таблицы); WARN/CRIT — по доле хостов (50 / 80 %),
    CRIT — ещё и при ×≥ 2;
  - прочие метрики из `--metrics` — по доле хостов (50 / 80 %), CRIT — при ×≥ 2 (↑) или ×≤ 0.5 (↓).

  Компоненты разных метрик одного события (начала в пределах 1.5 интервала или перекрытие не меньше половины
  более длинного) дают **одно замечание** `CLUSTER_SYNC`: метрика — список компонентов (`disk.write↓ + net.write↑ +
  top.java.cpu↓`), значение — % хостов самого серьёзного компонента, в пороге — критерий, давший уровень
  (`провал ×≤ 0.5 у ≥ 80% хостов, 6 интервалов ≥ 5 → CRIT`), уровень — максимум по компонентам; в фактах по каждому
  компоненту — уровень, тип, длительность, k из n хостов, ×, фон → уровень в эпизоде и Δ, объём; в JSON — поля
  самого серьёзного компонента `ratio`, `base`, `level`, `peak` (max для ↑, min для ↓), `unit`, `volume` (GB, у
  net/disk), длительность события `duration_s`, `balance_gb` (Σ избытка tx/rx набора, у событий с `net.*↑`) и
  массив `components` (то же по каждому компоненту).
  Подсказка для `net.*↑` строится по **балансу трафика** самого набора хостов: Σ избытка tx и Σ избытка rx за окно
  события; rx < 0.2 × tx — трафик уходит за пределы анализируемых хостов (клиенты, внешние системы, узлы без данных
  nmon), rebalance между ними исключён; tx < 0.2 × rx — трафик приходит извне; сопоставимы — обмен внутри набора
  (rebalance, снапшот, репликация); объём ≥ 1 GB — не сообщения PME. Провал активности на фоне такой передачи — не
  остановка узлов, а смена профиля нагрузки или блокировка обновлений (сверить с логами Ignite: exchange,
  rebalance, snapshot, клиентские запросы); без массовой передачи — блокировка операций (PME/exchange), пауза
  клиентской нагрузки, сетевое событие. **Первый хост**
  указывается, только если он опередил всех остальных не меньше чем на 0.9 интервала (значения nmon — средние за
  интервал, разница в секунды о порядке ничего не говорит) **и** ни у одного другого хоста эпизода в снимке
  лидера (ближайшем, не дальше половины интервала) ещё нет отклонения того же знака хотя бы в половину порогов
  выброса (|z| ≥ `--z`/2 и отклонение ≥ ½ минимального): порог z разные хосты пересекают в разное время, а
  изменение могло начаться у всех в одном интервале; иначе «одновременно». Порядок надёжен только при
  синхронных часах. Если у хостов меньше 5 снимков — текст «мало для поиска выбросов»;
- **кластерный таймлайн** (границы корзин кратны шагу; для mean и sum по каждому хосту сначала берётся среднее
  по его снимкам в корзине, затем mean cpu по хостам или сумма disk/net/java по хостам, у которых метрика есть;
  для max (blocked, busy) — максимум по всем снимкам корзины всех хостов);
- **неполное покрытие** и `CLUSTER_COVERAGE`: хост «закончился раньше» (вероятное падение узла), только если позже
  его конца (на ≥ порога WARN снимков) данные есть у ≥ половины остальных хостов (и не меньше 2 при ≥ 3 хостах);
  число снимков — до медианы концов этих хостов, в фактах — «данные есть у K из N остальных хостов до …». Один
  хост, записанный дольше остальных, никого «упавшим» не делает: в таблице — строки «конец позже медианы» /
  «конец раньше медианы» / «начало позже медианы» (относительно медианы концов и начал хостов) и разрывы;
- **замечания уровня кластера** (по времени внутри уровня severity) и **health по хостам** (число CRIT/WARN и коды).

Код возврата учитывает и кластерные замечания, и health по хостам — все, независимо от
`--no-info`/`--min-severity` (эти опции фильтруют только показанные кластерные замечания).

### `export` — выгрузка данных
Опции: `--section NAME` (`CPU_ALL`, `MEM`, `DISKWRITE`, `JFSFILE`, `TOP`, `UARG`, …) с `--columns REGEX...`,
либо `--metrics имена...`; `--step`/`--agg` агрегируют и метрики, и колонки секции (границы корзин и смысл
`--agg sum` — как в `timeline`: скорости `/s` умножаются на фактический шаг снимка и дают количество за корзину, о чём
говорит примечание таблицы; приращения за интервал — VM, кроме `nr_*`, — складываются как есть; для уровней
— `WARN`); `--limit N` ограничивает число строк (в том числе для TOP и UARG). Все строки
получают реальную метку времени. С `--format csv` удобно для собственного скрипта агента: первая колонка —
`host` (всегда, в том числе для одного файла), затем `time` (для `--section UARG` — `first_seen`) и данные; при
нескольких хостах каждая таблица предваряется строкой `# <host> | Экспорт | <секция или metrics>` и отделена
пустой строкой (раздел 8);
`--format json` даёт строки как объекты, ключ = имя колонки.

`--section TOP` выгружает все поля процесса (`--columns` принимает и имена колонок заголовка TOP nmon: `ShdLib` =
`shdlib_kb`, `%CPU` = `cpu_pct` …) в порядке: `time, pid, command, cpu_pct, usr_pct, sys_pct, size_kb,
rss_kb, restext_kb, resdata_kb, shdlib_kb, minflt, majflt, threads, iowait` (shdlib_kb нужен, например, для
«анонимной» RSS = rss_kb − shdlib_kb); `--columns` фильтрует эти имена (regex, полное совпадение; `time`
остаётся всегда). `--section UARG` выгружает по строке на PID: `first_seen, pid, prog, cmdline` (`first_seen` —
первое появление командной строки в UARG); `--columns` фильтрует эти имена, `first_seen` остаётся всегда. К TOP и
UARG `--step/--agg` не применяются (строки процессов выгружаются как есть) — об этом печатается WARN.

Если выгружать нечего — секции нет, ни одна колонка не подошла под `--columns`, нет TOP/UARG (или в окне нет
снимков с TOP), не найдена ни одна метрика (в том числе `top.<cmd>.*` с процессом, которого нет в данных) или ни
у одной из `--metrics` нет значений, — причина печатается в stderr как `WARN: <host>: …` (со списком имеющихся
секций или колонок). Если данных нет ни по одному хосту, команда завершается с кодом 3 и сообщением
`ERROR: export: нет данных …`; если данные есть хотя бы по одному хосту — код 0, по остальным только WARN.

### `bbbp` — конфигурационные блоки
Опции: `--block REGEX` (`lscpu`, `/proc/meminfo`, `/bin/df-m`, `/bin/mount`, `/etc/fstab`, `ifconfig`,
`netstat -r`, `/proc/diskstats`, `/proc/partitions`, `/proc/modules`, `/etc/release`, `uptime`…),
`--grep REGEX` (по строкам всех блоков), `--limit N` (строк на блок, по умолчанию 400; `0` — без ограничения;
при усечении печатается «… ещё K строк»). Без опций — список блоков с числом строк.

### `sections` и `metrics`
`sections` — какие секции есть: число колонок и значений, единицы, **полный список колонок** (точные имена для
`raw.<SECTION>.<column>` и `export --columns`; у TOP — имена `export --section TOP`: `pid`, `cpu_pct`, `shdlib_kb` …,
а исходные имена nmon `PID`, `%CPU`, `ShdLib` … — в описании; в text/md показаны первые 12 и «+K», в JSON — весь
список) и описание секции (для VM: `nr_*` — текущие значения в страницах, остальные — приращения за интервал,
pgpgin/pgpgout в KB); блоки BBBP.
`metrics` — имена метрик для данного файла с единицами: базовые, по ядру — `cpu.core<N>.busy`, по команде TOP —
`top.<cmd>.cpu`; остальные поля — по шаблонам из примечания таблицы (раздел 5). Колонка «значений» — число снимков
с числом (у `top.*.cpu|usr|sys|majflt|minflt` снимок TOP без процесса = 0, поэтому там это все снимки с TOP),
«снимков в TOP» — сколько раз процесс действительно был в TOP (1 — мелькнул один раз). Ядерные потоки с `/` в
имени (`kworker/…`, `ksoftirqd/N`, `migration/N`, `irq/…`) перечисляются одним именем по префиксу
(`top.kworker.cpu` — сумма по всем kworker, так как `top.<cmd>` сопоставляется по префиксу; отдельную группу
задач можно запросить по имени из `top --by-cmd`, например `top.kworker/*-writeback.cpu`); имена
`cpu.core<N>.busy` строятся по фактическим секциям CPUnnn (нумерация может быть с разрывами).

Используются в `timeline`, `events`, `correlate`, `compare`, `export --metrics`, `at --metrics`, `cluster --metrics`.

Метрики TOP: для полей cpu, usr, sys, majflt, minflt снимок с данными TOP, где процесса нет, даёт **0** (в TOP не
попадают процессы ниже порога CPU — и несуществующие), поэтому остановка JVM видна в `timeline`/`correlate`, а
средние в `timeline`/`cluster` — за всё время, а не только за снимки присутствия; снимки без TOP (первый снимок
файла, разрывы, nmon без `-t`) — NaN. Поля rss, vsz, threads, iowait у отсутствующего процесса — NaN (у
`top.java.*` — см. таблицу: сумма по основным JVM с последним известным значением). Процесс,
который есть в данных, но не виден в TOP окна `--from/--to` (или окна `compare`), даёт в окне 0, а не пустой ряд;
если процесс не встречается ни в одном снимке данных (опечатка в имени или PID), метрика `top.<cmd>.*`
считается отсутствующей — `WARN`, а `export` без единой найденной метрики завершается с кодом 3.

## 6. Правила health: коды, пороги, смысл

Формат порога: `WARN / CRIT`. «↓» — хуже, когда значение меньше. Переопределение: `--thr CODE=WARN[,CRIT]`.
Для правил с порогом «—» (`JAVA_START`, `THP_ACTIVE`, `THP_COMPACTION`, `NO_SWAP`, `CHECKPOINT_PERIOD`) и для
`JAVA_RESTART` `--thr` принимается, но не влияет на результат (печатается `WARN`; `JAVA_START` использует WARN
правила `JAVA_GONE`); у `NMON_EMPTY`, `WINDOW_SHORT`, `DATA_QUALITY`, `MEM_FORMAT`, `NMON_AIX`, `NMON_FIRST_ONLY`
порога нет — `--thr` для них — `ERROR: неизвестный код`.
Правила по рядам CPU, PROC (RUNQ_*, BLOCKED_*), памяти и VM (MEM_*, SWAP_*, DIRECT_RECLAIM, KSWAPD_ACTIVE,
MAJFAULT_HIGH), дисков (DISK_*, IO_STALL, CHECKPOINT_PERIOD) и сети (NET_*) считаются без первого снимка каждого
файла (T0001, неполный интервал); если кроме первых снимков в выборке ничего нет — не считаются (INFO
`NMON_FIRST_ONLY`); FS_* — по всем снимкам (JFSFILE — уровень заполненности), правила по BBBP —
по блокам на старте nmon.
Правила `*_RUN` — эпизодные: длительность эпизода — по меткам времени + интервал, на пропуске данных > 5 интервалов
эпизод разрывается (у `RUNQ_RUN` и `BLOCKED_RUN` — промежуток между первым и последним отсчётом, эпизод рвёт любой
пропуск снимка: Runnable и Blocked — мгновенные значения); время замечания — начало самого длинного эпизода. Порог
эпизода `CPU_SATURATION_RUN`, `RUNQ_RUN`, `BLOCKED_RUN` и `DISK_BUSY_RUN` — WARN правила за весь период
(`CPU_SATURATION`, `RUNQ_HIGH` × CPU, `BLOCKED_HIGH`, 90 % как у `DISK_BUSY_SUSTAINED`) с учётом `--thr`, тот же, что у
эпизодов `cpu` и «Эпизодов превышения порогов» `events`. Без CPU_ALL/PROC/CPUnnn или без числа CPU
соответствующее правило пропускается. Тренды (`MEM_GROWTH`, `FS_GROWTH`, `JAVA_RSS_GROWTH`) — «надёжные» при
r² ≥ 0.7 (у `FS_GROWTH` ещё рост ≥ 0.05 п.п./ч), то же условие, что у времени до исчерпания в `mem` и `fs`.

| Код | Что измеряется | WARN / CRIT | Что обычно означает для Ignite |
|---|---|---|---|
| `CPU_SATURATION` | CPU busy p95, % | 80 / 95 | CPU-насыщение: пулы Ignite, SQL, GC, rebalance |
| `CPU_SATURATION_RUN` | самый длинный эпизод busy > WARN `CPU_SATURATION` (80 %; с учётом `--thr`) ≥ 2 снимков подряд, мин; CRIT — только если max busy в эпизоде ≥ CRIT `CPU_SATURATION` (95 %), иначе не выше WARN; не выдаётся, если `CPU_SATURATION` уже той же или более высокой серьёзности | 5 / 15 | короткое насыщение, которое p95 за весь период не видит (инцидент в длинном файле); в фактах — интервал, max/avg busy, порог эпизода, число эпизодов, max Runnable, топ-процесс |
| `CPU_WAIT` | iowait avg, % | 10 / 25 | CPU ждёт диск: checkpoint/WAL/снапшот, медленный диск |
| `CPU_WAIT_PEAK` | iowait max, % | 30 / 60 | кратковременный I/O-шторм |
| `CPU_STEAL` | steal max, % | 1 / 5 | гипервизор отбирает CPU: риск таймаутов failure detection |
| `CPU_SYS_SHARE` | доля sys в busy (Σ sys / Σ busy), % (при busy avg > 5 %); WARN/CRIT только при sys avg ≥ 10 % всех CPU, иначе INFO; в фактах — sys в ядрах из N, медиана/p95 доли по снимкам, pswitch на CPU и r(Sys%, pswitch) | 40 / 60 | page faults/THP, softirq сети, futex, слишком много потоков; на Linux Sys% включает irq/softirq. INFO — доля высока при малом абсолютном sys: профиль нагрузки (много потоков, переключения контекста), значимо, если доля растёт в окне инцидента |
| `CPU_HOT_CORE` | % снимков с ядром > 90 % при общей busy < 50 % | 20 / 50 | однопоточное узкое место (один поток Ignite/GC); ядро с sys ≫ user — обработка прерываний сети |

| `OVERCOMMIT` | Committed_AS / MemTotal на старте | 1.0 / 1.5 | обещано больше памяти, чем есть |
| `COMMIT_LIMIT` | Committed_AS / CommitLimit на старте (BBBP); замечание от 0.9. WARN/CRIT — только если CommitLimit отличается от значения по умолчанию ((MemTotal − Hugetlb) × 50 % + SwapTotal) больше чем на 2 % RAM (изменены `vm.overcommit_ratio` / `overcommit_kbytes` — признак режима `vm.overcommit_memory=2`), иначе INFO; при отношении > 1.01 — INFO: в режиме 2 ядро не даёт Committed_AS превысить CommitLimit, превышение возможно только после уменьшения лимита (swapoff, sysctl, резерв hugepages), вероятнее режим 0/1 | 0.9 / 0.98 | при `vm.overcommit_memory=2` выделение сверх CommitLimit завершается ENOMEM (unable to create native thread, ошибка выделения off-heap); при режимах 0/1 — информативно; режим в BBBP не виден — проверьте `sysctl vm.overcommit_memory`; значение на момент старта nmon |
| `NO_SWAP` | INFO: swap не настроен | — | норма для Ignite; при нехватке памяти сработает OOM-killer |
| `CLUSTER_OUTLIER` | \|z\| хоста относительно медианы кластера (≥ 4 хостов с ≥ 10 снимками; агрегаты в общем окне, без первых снимков файлов); z по медиане/MAD, при MAD = 0 — по среднему абсолютному отклонению, масштаб не меньше 5 % медианы; отличие ≥ 10 % медианы и ≥ минимального абсолютного (раздел 4, `cluster`); CRIT — только при отличии ≥ 50 % медианы и ≥ минимального абсолютного для CRIT (cpu.* — 5 п.п., mem.* — 1 GB, disk.*/net.* — 10000 …); без общего окна — не выше WARN, `:max`/`:min` не сравниваются; у метрик с правилом health (`cpu.busy`, `cpu.wait`, `cpu.steal`, `proc.*`, `mem.avail_cal`, `mem.swap_used`, `disk.busy_max`, `top.java.rss`, `top.java.threads`) WARN/CRIT — только на плохой стороне и при ≥ 50 % WARN-порога правила, иначе INFO; одно замечание на хост (все его выбросы — в фактах и `components`) | 3 / 5 | узел отличается от остальных; `net.*` ниже медианы — узел обменивается меньше (распределение партиций, baseline, клиентская нагрузка); INFO — неоднородность нагрузки в пределах здоровых уровней |
| `CLUSTER_SYNC` | одно замечание на синхронное событие: компоненты `метрика↑` (всплеск или плато) / `метрика↓` (провал) с началом в пределах 1.5 интервала или перекрытием ≥ половины более длинного; участники — хосты, у которых среднее в эпизоде против фона до него ×≥ 1.25 (↑) или ×≤ 0.8 (↓); нужно ≥ max(3, ⌈20 % N⌉) участников и ≥ 50 % хостов с данными; значение — % хостов самого серьёзного компонента, в пороге — критерий уровня; рост нагрузки (`cpu.busy`, `disk.*`, `net.*`, `top.java.cpu` ↑) — INFO, WARN при стрессе выше WARN health у ≥ половины участников или вместе с провалом активности, CRIT не выдаётся; провал активности (те же ↓) — WARN при ×≤ 0.5, ≥ 80 % хостов, ≥ 2 интервалов, CRIT — ещё при ×≤ 0.2, ≥ 5 интервалов или стрессе, слабее — INFO; стресс (`cpu.wait`, `proc.blocked`, `disk.busy_max`, `proc.runq` ↑) — только при пике выше WARN health, WARN/CRIT по доле 50 / 80 %; в фактах — по компонентам ×, фон → уровень и Δ в единицах метрики, объём (GB), длительность; в JSON — `ratio`, `duration_s`, `base`, `level`, `peak`, `volume`, `balance_gb`, `components` (раздел 4, `cluster`) | 50 / 80 (доля хостов) | рост нагрузки — распределённая нагрузка (запросы, загрузка, rebalance, checkpoint по расписанию); `net.*↑` — по балансу Σtx/Σrx набора: трафик наружу/извне или обмен внутри набора (rebalance/снапшот), объём ≥ 1 GB — не PME; провал активности — блокировка операций (PME/exchange), пауза клиентской нагрузки, сетевое событие, а на фоне массовой передачи — смена профиля нагрузки или блокировка обновлений |
| `CLUSTER_COVERAGE` | хост закончил данные раньше других, снимков: только если позже его конца данные есть у ≥ половины остальных хостов (и ≥ 2 при ≥ 3 хостах), отсчёт — до медианы их концов | 3 / 10 | узел или nmon остановился раньше остальных; один хост, записанный дольше, замечаний не создаёт (строка «конец позже медианы» в таблице) |

Пороги подобраны консервативно под серверы Ignite с persistence; для других ролей меняйте через `--thr`.

## 8. Форматы вывода, JSON, коды возврата

- `text` (по умолчанию): заголовок — строка `<отчёт>  [host]` между двумя линиями из `=`, блоки
  `--- <название> ---`, таблицы с выровненными колонками, `(показано N из M)` при усечении, `(примечание)` под
  блоком; замечания — `[SEV] CODE @ время: метрика = значение (порог …)`, дробное значение и порог — с точностью,
  по которой их можно сравнить (|v| < 1 — 3 знака, < 10 — 2, иначе 1: `0.923`, а не `0.9` при пороге `≥ 0.92`).
- `md`: те же блоки в Markdown: `# <отчёт> — host`, `## <блок>`, таблицы `| … |` (символ `|` в ячейках
  экранируется как `\|`, переводы строк — `<br>`), kv-блоки — список `- **ключ**: значение`, замечания — список
  `- **[SEV] CODE** [host] @ время: метрика = значение (порог …)` с вложенными пунктами `- факты: …` и
  `- подсказка: …`, текстовые блоки (полоса покрытия, сырые строки BBBP, сообщения) — в блоке кода ```` ``` ````;
  `(показано N из M)` и примечание `_…_` отделены от таблицы пустой строкой.
- `json`: массив отчётов (один на хост; для `cluster` — один отчёт):

```json
[{"title": "…", "host": "node01",
  "blocks": [
    {"type": "kv", "title": "…", "items": {"ключ": "значение"}, "units": {"ключ": "MB"}, "note": null},
    {"type": "table", "title": "…", "columns": ["a", "b"], "rows": [{"a": 1, "b": "x"}], "units": {"a": "KB"},
     "note": null, "total_rows": 10},
    {"type": "text", "title": "…", "text": "…"},
    {"type": "findings", "title": "…", "items": [
       {"severity": "CRIT", "code": "DISK_BUSY", "host": "node01", "time": "2026-03-14 03:00:08",
        "metric": "busy p95 nvme0n1 (/opt/ignite/db)", "value": 98.7, "threshold": "≥ 80.0",
        "evidence": "…", "hint": "…"}]}]}]
```
  NaN/inf сериализуются как `null`, времена — строки `YYYY-MM-DD HH:MM:SS`, дробные числа округлены до 3 знаков.
  Числа в JSON без форматирования: значения kv-блоков и таблиц, которые в text/md печатаются в удобных единицах
  (`1.7 TB`, `2h 05m`), в JSON — числа, а их единицы — в поле `units` блока (`{колонка или ключ: "KB" | "MB" |
  "s"}`; например, в `info` memtotal — MB, длительность — s, MemAvailable — KB; в `cpu`, `cores`, `proc` колонки
  «время», «время > 90%», «длительность» — секунды). Колонки и ключи, которых нет в
  `units`, — числа в единицах, указанных в имени (`KB/s`, `%`, `ms`, `MB`) или в колонке `ед.`; `units` бывает
  пустым `{}`. Блоки `java[<pid>]` команды `java` — числовые: каждый показатель отдельным ключом (`%CPU p95`,
  `RSS max` в MB, `threads конец`, `major faults avg, /s` …), строками остаются только пояснения; в «Оценке памяти
  java[<pid>] по флагам» (`uarg`, `java`) размеры — числа в MB, строка — только у незаданного значения («не задан
  …»). Так же устроены kv-блоки «Ядра» `cpu`, «Физические ядра» `cores`, «Учёт CPU» `top`, «Грязные страницы» `vm`
  (MB в `units`) и «Контекст» `proc` (load average 1/5/15, Runnable + Blocked первых снимков): каждое число —
  отдельным ключом, время — отдельным ключом-строкой. Замечания `CLUSTER_SYNC` и `CLUSTER_OUTLIER` несут
  дополнительные поля (раздел 4, `cluster`): у `CLUSTER_SYNC` — `ratio`, `duration_s`, `base`, `level`, `peak`,
  `unit`, `volume` (GB), `balance_gb` (`{"tx": …, "rx": …}` или `null`) и `components` (по компоненту: `metric`,
  `severity`, `criterion`, `kind`, `start`, `end`, `duration_s`, `hosts`, `present`, `share`, `ratio`, `base`,
  `level`, `peak`, `unit`, `volume`); у `CLUSTER_OUTLIER` — `components` (`metric`, `value`, `median`, `pct`, `z`,
  `severity`). PID процесса после перезагрузки ОС внутри данных (раздел 9) в тексте — `pid@HH:MM`, в JSON — число.
  Списки имён
  (колонки секций в `sections`, «мёртвые» колонки в `check`) в JSON — полные массивы строк; в text/md
  показываются первые 12 и «+K». Исключения — текстовые сводки, которые остаются строками: kv «Ключевые
  показатели» `report` (составные строки вида `avg / p95 / max`), «Различия конфигурации» `cluster` и колонка
  «между» таблиц смены PID (`top`, `java`: `5m 00s`).
- `csv`: таблицы, замечания и kv-блоки (в том числе замечания `check` и «Предупреждения разбора» `info` — это
  таблицы); текстовые блоки (сообщения, полоса покрытия) пропускаются — если в выводе нет ничего, кроме них,
  печатается `WARN: в отчёте нет табличных данных для csv — используйте --format json` (кроме отчётов, где данных
  нет и причина уже напечатана, например пустой `export`: тогда stdout пуст). Раскладка:
  - таблица отчёта по хосту — первая колонка `host` (всегда, даже для одного файла: схема не зависит от входа),
    дальше колонки блока; у отчёта `cluster` и `questions` колонки остаются как есть (где нужно, `host` уже есть
    в самой таблице);
  - замечания — таблица `host,severity,code,time,metric,value,threshold,evidence,hint` (для кластерных замечаний
    `host` — имя хоста или `*`);
  - kv-блок — таблица `host,block,key,value` (`block` — название блока; у `cluster` `host` пустой);
  - блоки разделены пустой строкой; если блоков в выводе больше одного, перед каждым идёт строка
    `# <host> | <отчёт> | <блок>` (у кластерного отчёта вместо host — `*`). Одна таблица (например, `export`
    по одному файлу) — обычный CSV без строки `#`.

  NaN/inf → пустая ячейка; дробные числа записываются с округлением до 6 знаков (без шума суммирования вида
  `1234.5000000001`, малые значения `/s` не теряются); числа — в тех же единицах, что в JSON (без форматирования
  `mb`/`kb`/`dur`), а единица колонок и ключей, которые в JSON описаны полем `units`, — в скобках в имени колонки
  (или ключа kv): `записано всего (KB)`, `размер (MB)`, `время > 80% (s)`; если единица уже есть в имени
  (`Δ, MB`), она не повторяется; времена — `YYYY-MM-DD HH:MM:SS`; списки — через запятую в одной ячейке. Пример разбора:
  разбить вывод по пустым строкам, в каждом куске пропустить строку `#` и читать как обычный CSV.
- Коды возврата: `0` — успех; для `health`, `report`, `cluster` — `1`, если есть WARN, `2`, если есть CRIT —
  по **всем** замечаниям: `--no-info`/`--min-severity` меняют только вывод (для `cluster` учитываются и
  кластерные замечания, и health по каждому хосту; удобно в скриптах). `3` — ошибка данных или аргументов с
  сообщением `ERROR: …` в stderr (нет файлов nmon, неверное время, длительность, окно, окно без снимков, `compare`
  без `--a`/`--b` или с окном без снимков ни у одного хоста, порог `--thr`, колонка
  сортировки, неизвестный код правила, недоступный `--output`), в том числе ошибка синтаксиса argparse
  (неизвестная опция, нечисловое значение — usage и `error: …`); для `export` — `3` с `ERROR: …`, если
  выгружать нечего ни по одному хосту (нет секции, не подошли `--columns`, нет TOP/UARG, не найдена ни одна
  метрика или ни у одной из `--metrics` нет значений; причины — в `WARN:`), и `0`, если данные есть хотя бы по
  одному хосту. Таким образом 0/1/2 — это
  результат, 3 — сбой. Предупреждения печатаются в stderr с префиксом `WARN:` и не мешают выводу.
- Вывод детерминирован: одинаковые входные данные и аргументы дают одинаковый текст.
- Внутренняя ошибка скрипта (не ошибка данных или аргументов) — трассировка и `ERROR: внутренняя ошибка …` в
  stderr, код `3` (никогда не `1`/`2`). Если читатель закрыл pipe (`| head`), остаток вывода отбрасывается без
  сообщений, код возврата — код результата.

## 9. Семантика данных nmon (что нужно знать, чтобы не ошибиться)

- **Время.** Метка снимка `ZZZZ` — момент завершения интервала; значения секций — средние за
  предшествующий интервал (`AAA,interval`, обычно 60 с): событие в 10:00:30 попадает в снимок 10:01, а не в
  ближайший 10:00 (так выбирает снимок `at`). Время — локальное время хоста без зоны. Первый
  снимок `T0001` охватывает неполный интервал (~1–2 с от запуска nmon), TOP начинается с `T0002`; статистика рядов
  в `report`, `health`, `cluster` и в сводках `cpu`, `cores`, `proc`, `mem`, `vm`, `disk`, `net`, `events`,
  `correlate`, `compare` считается без первого снимка каждого файла и запуска (суммы приращений VM «за период» — по
  всем снимкам; `fs` и `FS_*` — по всем: JFSFILE — уровень), `--skip-first` убирает его и из остальных команд
  (`at`, `timeline`, `export` и т. д.). Объёмы «за период» (disk, net, NETERROR, сверки `check`) — Σ скорости ×
  фактический шаг снимка (после разрыва — его длительность, у первого снимка запуска — время от старта nmon по
  `AAA,date/time`, с учётом `--tz-shift`), как в `export --agg sum`; «время выше порога» — сумма фактических
  длительностей снимков выше порога. Сравнение с логами в другой зоне — через `--tz-shift` (сдвигает только метки:
  ни одна величина от него не меняется).
- **CPU_ALL** — проценты от всех логических CPU; `Busy` пустая (не считается nmon); `Steal%` есть у nmon ≥ 14.
  `CPUnnn` — по каждому логическому CPU, нумерация с 1 (CPU001 = cpu0). `Sys%` в nmon для Linux = system + irq +
  softirq (как это читать — раздел 4, `cpu`); разбивку system/irq/softirq по CPU за период nmon не даёт — только с
  загрузки ОС в BBBP `/proc/stat` (см. `cores`).
- **MEM** — в MB. `cached` включает tmpfs/shmem (`memshared`, он же `Shmem` в meminfo), которые не
  вытесняются, поэтому скрипт считает `avail ≈ memfree + buffers + (cached − memshared) + slab reclaimable`; эта
  оценка выше MemAvailable примерно на постоянную величину в MB — резервы ядра (почему и насколько — раздел 4,
  `mem`). Точное значение на старте есть в meminfo, по нему калибруются `mem.avail_cal` и `MEM_AVAIL_LOW`.
  `-0.0`/`-1.0` = не поддерживается.
- **VM** — первые шесть `nr_*` — текущие значения в страницах (скрипт переводит в MB по размеру страницы из
  `getconf PAGESIZE` в BBBP, по умолчанию 4 KB; на ядрах с 64 KB страницами это важно); остальные —
  **приращения с предыдущего снимка** (не за секунду): `pgpgin/pgpgout` в KB за интервал (скрипт переводит в
  KB/s, и это совпадает с суммой DISKREAD/DISKWRITE физических дисков), `pgfault/pgmajfault` — события за
  интервал (скрипт даёт /s), `pswpin/pswpout` — страницы за интервал. Метрики /s (`vm.pgpgin`, `vm.pgpgout`,
  `vm.pgfault`, `vm.pgmajfault`, `vm.pgfree`) делятся на фактический шаг снимка (как объёмы «за период», см.
  «Время»): после разрыва (хост или nmon стоял) приращение покрывает весь разрыв, и деление на номинальный interval
  завысило бы скорость кратно его длине; значения «за интервал» (`pswp*`, `pageoutrun`, `slabs_scanned`, …) после
  разрыва тоже покрывают весь разрыв. При переводе часов или скачке системного времени шаг по ZZZZ неверен для
  одного снимка. На современных ядрах счётчики `kswapd_steal`, `allocstall`, `pgscan_*`, `pgsteal_*`,
  `pgrefill_*`, `pgalloc_high/dma`, `pginodesteal`, `nr_unstable` всегда 0 (nmon читает старые имена; с каких
  версий ядра — раздел 4, `vm`). `report` помечает такие нули как `n/a` с учётом версии ядра из AAA,OS.
- **PROC** — `Runnable`/`Blocked` — мгновенные значения (`procs_running`/`procs_blocked`) в момент снимка, не
  средние; `pswitch`/`fork` — в секунду (в T0001 — 0); `syscall/read/write/exec/sem/msg` = −1 на Linux.
- **DISK*** — по всем блочным устройствам, включая разделы и dm-N (LVM): один и тот же ввод-вывод учитывается на
  физическом диске, его разделе и на dm-устройстве. Скрипт суммирует только физические устройства; для
  LV смотрите `--dev`/`--all` и распределение трафика по LV в `disk`. Снимок T0001 (1–2 с на старте nmon) в
  дисковой статистике не используется. `DISKBUSY` = util; `DISKXFER` = IOPS (чтение+запись вместе); `DISKBSIZE` =
  средний KB на операцию. Устройств больше `disks_per_line` (150) — nmon делит секции на DISKBUSY1…; скрипт
  склеивает. Латентность (DISKREADSERV/DISKWRITESERV) в типичных файлах nmon для Linux отсутствует.
- **JFSFILE** — % занятости с шагом 0.1 %; абсолютные размеры берутся из `df -m` на старте (BBBP).
- **NET/NETPACKET** — KB/s и пакеты/с по каждому интерфейсу; трафик bond дублируется на его слейвах, VLAN — на
  родителе, мостов и виртуальных интерфейсов — на физических портах (скрипт исключает их, слейвы и lo из сумм;
  роли — раздел 4, `net`). Ошибки/дропы — только накопительно на старте (ifconfig, /proc/net/dev; счётчики bond
  включают счётчики слейвов), если нет секции NETERROR (её значения — в секунду).
- **TOP** — только процессы с заметным CPU в интервале (порог ≈ 0.1 % ядра): отсутствие процесса в снимке с TOP
  = он простаивал или не существовал, поэтому метрики `top.*.cpu|usr|sys|majflt|minflt` в таком снимке равны 0;
  `%CPU` — в процентах одного ядра (может быть > 100);
  `Size` (VSZ), `ResSet` (RSS), `ResText`, `ResData`, `ShdLib` (file/shmem-backed часть RSS) — в KB;
  `MinorFault/MajorFault` — события **в секунду** (nmon делит приращение счётчиков процесса на длину интервала);
  `MajorFault` у JVM может на порядки превышать системный `VM pgmajfault` за те же интервалы: в
  счётчике процесса учитываются и faults, завершённые после повтора (retry — ожидание страницы под
  вводом-выводом или блокировки), а не только чтения с диска. `check` различает это по сверке с `VM pgfault`:
  если `Σ (Minor + Major)` или `Σ (Minor + 2·Major)` процессов TOP × шаг снимка ≈ `Σ pgfault` (0.85–1.1),
  колонка согласуется с системой и означает faults после повтора; если нет — помечается как ненадёжная. В
  обоих случаях для выводов о реальных чтениях с диска используйте `vm.pgmajfault`; `java` показывает долю
  faults после повтора у процесса и faults всего (minor+major) — у JVM они растут при первом касании памяти и
  записи в mmap-файлы (WAL, страницы persistence) и часто коррелируют с %sys процесса. `Threads`, `IOwaitTime` —
  только в nmon ≥ 16; `IOwaitTime` берётся из /proc/PID/stat главного потока и для многопоточных JVM остаётся 0
  даже при реальном ожидании I/O. Имя команды обрезано до 15 символов (comm), кроме kworker: в его имени — текущая
  задача workqueue (`kworker/u64:1-flush-253:0`), имя одного PID меняется от снимка к снимку (`java`,
  `report` и `top --by-cmd` группируют kworker по задаче). Нет PPID/UID/состояния процесса. **PID после
  перезагрузки ОС** внутри данных хоста (boottime файла/запуска сменился больше чем на 120 с) — другой процесс, даже
  если номер совпал: в выводе он показан как `pid@HH:MM` (время загрузки; в JSON колонка `pid` — число), у него
  своя жизнь и статистика, а смена основного JVM через перезагрузку — `JAVA_RESTART`. `--pid N` и `top.pid<N>.*`
  выбирают номер во всех эпохах загрузки.
- **UARG** — только при запуске nmon с `-T`; содержит полную командную строку (флаги JVM).
- **BBBP** — однократный снимок конфигурации в момент старта nmon (lscpu, meminfo, df, mount, fstab, lsblk,
  ifconfig, diskstats, uptime…). Изменения во время записи не видны.
- **Объединение файлов хоста** — по имени хоста из `AAA,host`; в перекрытии файлов остаются снимки более раннего
  (раздел 2); у файлов/запусков с разным `interval` каждый снимок интегрируется со своим интервалом; метаданные и BBBP берутся из самого раннего файла, но период, boottime, uptime, CPU,
  MemTotal и OS каждого файла и каждого запуска nmon в нём сохраняются отдельно (таблица файлов в `info`,
  перезагрузка/смена конфигурации между файлами — в `check`, перезагрузка во время наблюдения — `BOOT_RECENT` в
  `health`). Перекрывающиеся файлы разных машин с одинаковым `AAA,host` не объединяются (раздел 2).

## 10. Сценарии разбора инцидентов Ignite

Ниже — какие сигнатуры искать в nmon и какими командами. Во всех случаях итоговый вывод о причине делается
вместе с логами Ignite (`Checkpoint started/finished`, `Too many dirty pages`, `Long JVM pause`,
`Node FAILED/LEFT`, `Local node SEGMENTED`, PME/rebalance-сообщения) и GC-логами.

### 10.1. Долгие checkpoint, write throttling, «узел тормозит каждые N минут»
Сигнатуры: пики `disk.write` на диске persistence, регулярные с периодом ≈ `checkpointFrequency`
(`CHECKPOINT_PERIOD` — при интервале nmon 60 с трёхминутный цикл может не распознаваться как регулярный, тогда
смотрите таблицу пиков глазами), во время пиков `disk.busy_max` ≈ 100 %, `proc.blocked` ↑, `cpu.wait` ↑,
`top.java.cpu` проваливается или растёт sys-доля (`IO_STALL`, `BLOCKED_HIGH`, `CPU_WAIT`), `vm.nr_dirty`
растёт перед сбросом. Команды: `health`, `disk` (пики и периодичность, размер IO), `timeline node01.nmon
--metrics disk.write disk.busy_max proc.blocked cpu.wait top.java.cpu vm.nr_dirty`, `correlate --target
proc.blocked`, `at --time <момент из лога>`.
Уточнение: если пики записи идут на диск с большим средним IO и высоким svc≈ms (HDD/SAS; для NVMe svc≈ms
занижен — смотрите busy, Blocked, iowait) — диск не тянет; если IO мелкий
при огромном IOPS — много случайных страниц (маленький checkpoint buffer, большие data regions на медленном
диске). Проверьте `diskmap`: не делят ли WAL, persistence и архив один физический диск.

### 10.2. Узел выпал из топологии / segmentation / failure detection
Сигнатуры на пострадавшем узле: `NMON_GAP` (nmon сам не смог снять данные — хост «замер»), `JAVA_CPU_DROP` /
`JAVA_ABSENT` / `JAVA_GONE` (JVM исчезла из TOP до конца данных — узел больше не работал), `NET_ZERO` / `NET_DROP`
на bond/NIC (у изолированного узла трафик обычно падает не до нуля, а до остаточного служебного), `NET_BOND_MEMBER`
(отказ слейва bond), `CPU_STEAL` (в VM), `SWAP_ACTIVITY`, `CPU_SATURATION` + `RUNQ_HIGH` или их эпизодные варианты
`CPU_SATURATION_RUN` + `RUNQ_RUN` (потоки discovery не получают CPU). `CPU_SATURATION`/`RUNQ_HIGH` — устойчивая
нагрузка за весь период; короткие эпизоды ловят `CPU_SATURATION_RUN`/`RUNQ_RUN`; для известного момента
инцидента — `health --from/--to`. На остальных узлах: синхронный всплеск `top.java.cpu↑` в момент PME
(`CLUSTER_SYNC`); сигнатура блокировки операций на время exchange — **короткий** (единицы интервалов) провал
`disk.write↓`/`top.java.cpu↓` на всех узлах при **малом** объёме трафика (сообщения PME — мегабайты) и асимметрии
координатора (у одного узла `net.write↑` больше, чем у остальных); затем rebalance (10.4). Исходящий объём в
гигабайтах при Σ избытка rx ≪ Σ избытка tx по набору хостов (подсказка и `balance_gb` замечания `CLUSTER_SYNC`) — не
PME: трафик уходит к клиентам или узлам вне набора, а одновременный провал записи — смена профиля нагрузки или
блокировка обновлений на фоне массовой передачи; сверяйте с логами Ignite (exchange, rebalance, snapshot,
клиентские запросы). Команды: `cluster` (покрытие: узел, закончивший данные раньше; синхронные
выбросы с «первым хостом»), `check` (разрывы), `java`, `net`, `at --time <момент FAILED> <dir>`.
Оговорка: nmon не различает «узел замер сам» и «его исключили»; «первый хост» в `cluster` указывается, только если
он опередил остальных почти на интервал nmon (≥ 0.9) и у остальных в его снимке ещё не было отклонения того же
знака, и надёжен только при синхронных часах.

### 10.3. OOM-killer / перезапуск JVM / рост памяти
Сигнатуры: `JAVA_RESTART` (смена PID; RSS нового процесса мал) или `JAVA_GONE` (OOM-killer убил JVM, а перезапуска
в окне данных не было; короткая java-утилита после гибели узла перезапуском не считается; `JAVA_GONE` у нового PID —
повторная гибель после перезапуска; `JAVA_START` — JVM стартовала во время записи), перед этим `MEM_AVAIL_LOW`,
`JAVA_RSS` (анонимная RSS ≥ 85 % RAM — WARN, ≥ 95 % — CRIT), `KSWAPD_ACTIVE` и `MEM_FREE_LOW` на уровне WARN
(то есть с подтверждением давления), `MAJFAULT_HIGH` (по системному `vm.pgmajfault`, не по TOP), сжатие `mem.cached`, иногда `SWAP_*`. Отказ
выделения без OOM-kill (`unable to create native thread`, ошибка выделения off-heap) — `COMMIT_LIMIT` (при
`vm.overcommit_memory=2`). Рост после плато: `JAVA_RSS_GROWTH`, `MEM_GROWTH`, `JAVA_THREADS_GROWTH`. Команды:
`java`, `mem`, `vm`, `timeline node01.nmon --metrics top.java.rss mem.free mem.cached vm.pgmajfault`, `uarg` (Xmx,
MaxDirectMemorySize — сравните сумму с RSS и с размерами data regions из конфигурации). nmon не видит сам факт
OOM-kill — подтверждайте по dmesg/journal и логам Ignite.

### 10.4. Rebalance / снапшот / массовая загрузка / бэкап
Сигнатуры: всплески `net.read` (принимающие узлы) и `net.write` (отдающие), крупный пакет в пиках (B/pkt ~MTU в
таблице пиков `net`, `net.tx_size` у отдающих, `net.rx_size` у принимающих; среднее за период размыто фоном
мелких сообщений), `disk.read` на persistence у отдающих и `disk.write` у принимающих, рост `top.java.cpu`; при снапшоте —
последовательная запись (большой IO) на архивный/снапшотный том и рост `fs.<mount>.pct`; при бэкапе — процесс
из категории «бэкап/копирование» в `java` (другие процессы). В `cluster` — эпизоды (часто плато) `net.read↑`/`net.write↑` на
многих узлах сразу; rebalance **между** анализируемыми узлами виден как сопоставимые Σ избытка tx и rx (подсказка
«обмен внутри набора»); Σrx ≪ Σtx — получатель вне набора (клиенты, узлы без nmon). Одновременный провал
`disk.write↓` и `top.java.cpu↓` на всех узлах при массовой передаче — смена профиля нагрузки или блокировка
обновлений; короткий провал без объёма — скорее блокировка операций (PME/exchange, 10.2). Команды: `cluster` (кластерный таймлайн: суммарные
disk/net; синхронные выбросы; `--sort net.read:mean` — кто принимает больше), `net`, `disk --all`, `fs`,
`correlate --target net.read`.

### 10.5. Медленные операции при «нормальной» средней загрузке CPU
Сигнатуры: `CPU_HOT_CORE` / `CPU_HOT_CORE_RUN` (одно ядро на 100 % — один поток: checkpoint-thread,
exchange-worker, striped-пул на одной partition, GC-поток; горячее ядро с sys ≫ user — обработка сетевых
прерываний), `JAVA_SYS_SHARE` (page faults/THP/futex), `RUNQ_RUN` (очередь в коротком окне; `RUNQ_HIGH` — только
устойчивая за весь период), `THP_COMPACTION`. Для известного момента инцидента — `health --from/--to`. Горячее
ядро ищите через `cpu` (эпизоды горячего ядра: когда, какое ядро, сколько длилось) и `cores --sort max`; `events
node01.nmon --metrics cpu.core_max top.java.sys proc.runq` подходит только для одиночных всплесков — плато
(ядро на 100 % десятки минут) скользящая медиана не видит. Далее `java`, `at`. nmon не показывает, какой именно
поток горячий — берите thread dump/JFR.

### 10.6. Кончается место (WAL-архив, снапшоты, логи)
Сигнатуры: `FS_FULL`, `FS_GROWTH` с оценкой времени до 100 %, скачки заполненности в `fs`, растущая запись на
соответствующий диск. Команды: `fs`, `diskmap` (что за диск, сколько осталось), `disk --dev <LV>`.

### 10.7. Подозрение на долгие GC-паузы
nmon не видит GC. Косвенно: `JAVA_CPU_DROP` (JVM встала), либо, наоборот, всплеск `top.java.cpu` со
скачком `cpu.user` на всех ядрах (параллельный GC), `events --metrics top.java.cpu cpu.busy`. Сопоставьте с
`Long JVM pause` в логах Ignite и GC-логами; посмотрите `uarg` (тип GC, Xmx, AlwaysPreTouch).

### 10.8. Память под давлением без swap
Сигнатуры: `MEM_FREE_LOW` и `KSWAPD_ACTIVE` на уровне WARN (с подтверждением), `MAJFAULT_HIGH`, `mem.cached`
падает при росте `top.java.rss`, `disk.read` растёт (страницы читаются с диска вместо кэша), kswapd* в TOP.
Команды: `mem`, `vm`, `correlate --target vm.pgmajfault`, `timeline node01.nmon --metrics mem.cached mem.free
top.java.rss disk.read`. Для Ignite с persistence это удар по латентности чтений: размер data regions + heap не
должен вытеснять page cache под WAL и файлы partition. Запас на будущее — в блоке meminfo `mem`:
`Committed_AS − AnonPages − Shmem` (выделено, но ещё не тронуто) против MemAvailable.

### 10.9. Виртуализация и «соседи»
`CPU_STEAL` > 0 — гипервизор отбирает CPU (переподписка); ищите провалы `top.java.cpu` в те же моменты. Соседи
на самом узле — антивирус/бэкап/мониторинг с высоким CPU или IOwaitTime — блок «Другие процессы» в `java`.

### 10.10. Общая методика по кластеру
1. `info <dir>`, `check <dir>` — доверять ли данным, есть ли разрывы, все ли узлы покрыты.
2. `cluster <dir>` — выбросы, синхронные события, кто закончил раньше, health по хостам.
3. `report <host>` для подозрительных узлов; `at --time` для моментов из логов; `compare` «до/во время».
4. Подсистемные команды по замечаниям; `export` для собственных вычислений.
5. Формулируйте выводы с указанием времени, хоста, метрики, значения и порога — так, как печатает `health`.

## 11. Чего nmon не показывает

- Внутренности JVM: GC-паузы, safepoints, занятость heap/off-heap/metaspace, состояния потоков, per-thread CPU
  (какой пул Ignite горячий), deadlock'и.
- Состояние Ignite: checkpoint buffer, dirty pages ratio, режим WAL, PME, rebalance, роли узлов, координатор.
- Латентность диска за период (await/svctm) — нет без `-D`/DISK*SERV; глубина очереди; fsync-счётчики; ввод-вывод
  по процессам и файлам (какой процесс писал в WAL).
- TCP/UDP: соединения, retransmits, RTT, backlog, ошибки во времени (без NETERROR); кто с кем обменивался
  трафиком; состояние bond/LACP; скорость линка.
- Load average во времени (только на старте), PSI, per-cgroup лимиты и OOM в cgroup, dmesg (OOM-killer, hung
  task, link down), sysctl (swappiness, dirty_ratio, THP mode), ulimit.
- Per-NUMA память во времени, THP/compaction-счётчики, NUMA-локальность.
- Всё короче интервала (10–60 с): 2-секундная пауза GC или 5-секундный fsync-шторм усредняются.
- Часовой пояс и рассинхронизация часов между узлами.
- Процессы ниже порога TOP, короткоживущие процессы между снимками, RSS idle-процессов.
- Ожидание I/O по процессу (IOwaitTime в TOP считается только для главного потока) и чтения с диска по процессу
  (колонка MajorFault в TOP включает и faults, завершённые после повтора, — см. `check`; реальные чтения видны
  только в системном `vm.pgmajfault`).
- Причины vs следствия: nmon показывает симптомы на уровне ОС; причина подтверждается логами Ignite/JVM.

## 12. Рекомендации по сбору nmon

Для последующего анализа Ignite полезно запускать nmon так:

```bash
nmon -fT -s 30 -c 2880 -m /var/log/nmon      # -T = TOP + командные строки (флаги JVM), 30 с × 24 ч
```

- `-T` вместо `-t`: даёт UARG (флаги JVM, роль процесса).
- Интервал 10–30 с лучше ловит короткие события (checkpoint, всплески); 60 с — минимально приемлемо.
- `-D` (если версия поддерживает) добавляет времена обслуживания дисков (DISKREADSERV/DISKWRITESERV).
- `-g файл_групп` позволяет объединить устройства WAL/persistence/архива в группы (DGBUSY…).
- Синхронизируйте часы узлов (chrony/NTP), иначе кластерный анализ порядка событий недостоверен.
- Не запускайте два nmon одновременно на одном хосте; если запустили — скрипт дедуплицирует, но первый
  интервал каждого файла будет неполным.

## 13. Приложение: секции nmon и их единицы

| Секция | Содержимое | Единицы / особенности |
|---|---|---|
| AAA | метаданные запуска: host, OS, date/time, interval, snapshots, cpus, boottime, command, version | |
| BBBP | конфигурация на старте: /etc/release, fdisk, lsblk, lscpu, /proc/cpuinfo, /proc/meminfo, /proc/stat, /proc/net/dev, /proc/diskstats, /dev/mapper, /proc/partitions, /proc/modules, ifconfig, df -m, mount, fstab, netstat -r, uptime, getconf PAGESIZE | однократно |
| ZZZZ | Tnnnn → HH:MM:SS, DD-MON-YYYY | конец интервала, локальное время |
| CPU_ALL | User%, Sys%, Wait%, Idle%, Steal%, Busy (пусто), CPUs | % всех CPU |
| CPUnnn | User%, Sys%, Wait%, Idle%, Steal% | % одного логического CPU |
| MEM | memtotal, memfree, cached, buffers, active, inactive, memshared, swaptotal, swapfree, swapcached, high*/low*/bigfree (N/A) | MB |
| VM | nr_* (gauge, страницы); pgpgin/pgpgout (KB/интервал); остальные — события/страницы за интервал | см. раздел 9 |
| PROC | Runnable, Blocked (мгновенные), pswitch, fork (/s), остальные −1 | |
| NET | <if>-read-KB/s, <if>-write-KB/s | KB/s |
| NETPACKET | <if>-read/s, <if>-write/s | pkt/s |
| NETERROR | ошибки по интерфейсам (редко) | /s |
| DISKBUSY | util по устройствам (диски, разделы, dm-N) | % |
| DISKREAD / DISKWRITE | чтение/запись | KB/s |
| DISKXFER | операций (чтение+запись) | /s |
| DISKBSIZE | средний размер операции | KB |
| DISKREADSERV / DISKWRITESERV | время обслуживания (только с -D) | ms |
| DGBUSY/DGREAD/DGWRITE/DGXFER/DGSIZE | группы дисков (-g) | как выше |

| UARG | Time, PID, ProgName, FullCommand (только -T) | |
| LPAR, POOLS, PAGE, MEMNEW, SEA, FC* | секции AIX | Linux-правила неприменимы |
