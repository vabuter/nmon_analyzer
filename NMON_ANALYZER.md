# nmon_analyzer.py — инструкция по анализу файлов NMON

Однофайловый скрипт на Python ≥ 3.12 (только стандартная библиотека) для анализа файлов
`nmon` (nmon for Linux) с узлов кластера Apache Ignite 2.17–2.19. Скрипт отвечает на вопросы
о поведении ОС на узле и в кластере: CPU, память, подкачка, диски, файловые системы, сеть,
процессы и JVM, качество самих данных nmon, сравнение узлов между собой.

Инструкция написана для ИИ-агента, который вызывает скрипт из shell. Структура:

## 1. Быстрый старт (рецепт для агента)

```bash
# 0. Какие команды есть и какой вопрос какой командой решается
python nmon_analyzer.py questions

# 1. Что за файлы: хосты, периоды, интервал, есть ли TOP/UARG, разрывы
python nmon_analyzer.py info /path/to/nmon/            # каталог со всеми файлами кластера

# 2. Можно ли доверять данным
python nmon_analyzer.py check node01.nmon

# 3. Общая картина по одному узлу: ключевые показатели + замечания (CRIT/WARN/INFO) + таймлайн
python nmon_analyzer.py report node01.nmon

# 4. Кластер целиком: покрытие, различия конфигурации, метрики по хостам, выбросы, синхронные события
python nmon_analyzer.py cluster /path/to/nmon/ --format md

# 5. Углубление в конкретную подсистему
python nmon_analyzer.py disk node01.nmon
python nmon_analyzer.py java node01.nmon
python nmon_analyzer.py mem node01.nmon

# 6. Что происходило в момент времени из лога Ignite (все метрики, процессы, диски, сеть)
python nmon_analyzer.py at --time "2026-03-14 03:52" node01.nmon

# 7. Ряд метрик вокруг инцидента, с укрупнением до 5 минут (max в корзине)
python nmon_analyzer.py timeline --around 03:52 --window 30m --step 5m --agg max node01.nmon

# 8. Что изменилось между «до» и «во время»
python nmon_analyzer.py compare --a 02:00-02:30 --b 03:30-04:00 node01.nmon

# 9. Машиночитаемый вывод
python nmon_analyzer.py health node01.nmon --format json
```

Порядок аргументов: пути к файлам ставьте **до** списковых опций `--metrics`/`--columns` (или отделяйте `--`),
иначе argparse примет путь за имя метрики. Скрипт возвращает в список путей завершающие элементы `--metrics`,
если они существуют как файлы, но надёжнее сразу писать `timeline node01.nmon --metrics cpu.busy disk.write`.
В Git Bash на Windows экспортируйте `MSYS_NO_PATHCONV=1`, иначе аргументы вида `/opt/…` (регулярные выражения
для `--mount`, `--dev`) будут переписаны в пути Windows.

Рекомендуемый порядок при разборе инцидента: `info` → `check` → `cluster` (если файлов много) →
`report` по подозрительным хостам → `health`/`events`/`at`/`timeline`/`compare` → `disk`/`mem`/`vm`/`net`/`java`
по подсистеме, на которую указывают замечания → `export` для собственных вычислений.

Каждое замечание (finding) содержит код правила, значение, порог, факты с временем и подсказку, что это
обычно означает для Ignite. Замечания можно цитировать в отчёте RCA как есть.

## 2. Входные данные

- Аргументы `paths`: файлы `*.nmon`, каталоги (обходятся рекурсивно, берутся файлы с расширением
  `.nmon`, `.nmon.gz`, `.nmon.txt`, `.nmon.csv`) и маски (`*.nmon`, `**/*.nmon` — раскрываются самим скриптом,
  поэтому работают и в Windows).
- Файлы `.gz` читаются напрямую.
- Если в одном файле несколько запусков nmon подряд (дописанный файл, `cat a.nmon b.nmon`), второй и следующие
  запуски распознаются по повторному `AAA,progname` или повтору `ZZZZ,T0001`; их снимки получают суффикс
  `#N` и не смешиваются с первым запуском (`info`/`check` сообщают об этом).
- Файлы группируются по имени хоста из строки `AAA,host`. Несколько файлов одного хоста **объединяются**
  в один ряд по времени; перекрывающиеся периоды (два nmon одновременно, или файл суток + короткий файл)
  дедуплицируются — снимки из разных файлов ближе, чем полинтервала, считаются одним (остаётся более ранний
  файл). Число отброшенных дубликатов показывает `info`. Отключить объединение: `--no-merge` (тогда каждый файл
  становится отдельным «хостом» `host:имя_файла`).
- Поддерживаются: несортированные и отсортированные файлы, CRLF, не-UTF-8 байты (заменяются), обрезанная
  последняя строка (nmon ещё пишет), отсутствие ZZZZ (время оценивается по `interval`), продолжения секций
  DISKBUSY1/DISKREAD1… при большом числе дисков, старые версии nmon без колонок Threads/IOwaitTime в TOP,
  файлы с AIX-секциями (LPAR, POOLS…) — общая статистика по ним доступна через `raw.<SECTION>.<column>` и
  `export`, но Linux-правила health к ним неприменимы; секция MEM формата AIX (без memtotal/memfree) в командах
  `mem`/`report`/`health` даёт сообщение вместо анализа памяти. Некорректные регулярные выражения в опциях,
  неверное время/длительность, окно с концом раньше начала, недоступный путь `--output` завершаются сообщением
  `ERROR: …` без трассировки.
- Требования: Python 3.12+, без зависимостей; работает на Linux/Windows/macOS. 30 файлов по 0.5–1.5 MB
  разбираются за 1–2 секунды.

## 3. Общие опции (всех команд)

| Опция | Смысл |
|---|---|
| `--host REGEX` | оставить только хосты, чьё имя матчится (можно несколько раз) |
| `--from T`, `--to T` | окно времени. `T` = `YYYY-MM-DD HH:MM[:SS]`, `YYYY-MM-DDTHH:MM`, `DD-MON-YYYY HH:MM` или просто `HH:MM[:SS]` (дата берётся от первого снимка хоста; если данные переходят через полночь и время раньше начала — берётся следующий день) |
| `--around T --window D` | окно `T ± D` (по умолчанию `D = 10m`; форматы длительности: `90s`, `10m`, `2h`, `1d`) |
| `--format text\|md\|json\|csv` | формат вывода (по умолчанию `text`); `csv` выводит только табличные блоки |
| `--output FILE`, `-o FILE` | записать вывод в файл |
| `--top N` | сколько строк/пиков показывать там, где применимо |
| `--no-merge` | не объединять файлы одного хоста |
| `--thr CODE=WARN[,CRIT]` | переопределить пороги правила health (см. раздел 6), можно несколько раз. Если CRIT не указан, берётся значение по умолчанию, но не «мягче» нового WARN (например, `--thr DISK_BUSY=99` даёт WARN 99 / CRIT 99); чтобы задать оба, пишите `--thr DISK_BUSY=99,100` |
| `--link-mbit N` | скорость сетевого линка в Mbit/s для оценки насыщения (nmon её не знает) |
| `--no-info` | не показывать замечания уровня INFO |
| `--min-severity CRIT\|WARN\|INFO` | показывать замечания не ниже уровня |
| `--skip-first` | отбросить первый снимок каждого файла и каждого запуска nmon внутри файла (T0001 охватывает неполный интервал) |
| `--tz-shift ±D` | сдвинуть все метки времени, например `--tz-shift=-3h` или `--tz-shift=+02:00` — чтобы сопоставлять с логами в другой зоне (nmon пишет локальное время хоста без зоны). Значение с минусом передавайте через `=` |
| `--verbose`, `-v` | ход разбора в stderr |

Фильтр времени применяется ко всем командам, включая `health` и `cluster` (статистика считается только по окну).

## 4. Справочник команд

Синтаксис: `python nmon_analyzer.py <команда> [опции] <paths...>`. Каждая команда, кроме `cluster` и
`questions`, выводит отдельный отчёт на каждый хост.

### `questions` — индекс вопросов
Печатает таблицу «вопрос → команда» и краткое напоминание общих опций. Не требует файлов.

### `info` — что это за файл(ы) и хост
Блоки: **Метаданные** (host, файлы, версия nmon, командная строка nmon с её опциями `-s/-c/-t/-T`, ядро,
boottime, заявленный и фактический интервал, число снимков, начало/конец, длительность, CPU, memtotal,
swaptotal, число дисков, физические диски, интерфейсы, число ФС, наличие TOP/UARG, отброшенные дубликаты,
число разрывов); **Разрывы во времени** (если есть); **Конфигурация (BBBP)** — модель CPU, сокеты/ядра/потоки,
NUMA, частоты, гипервизор, MemTotal/MemAvailable/Swap/HugePages/AnonHugePages/Committed_AS на старте,
uptime и load average на старте, дистрибутив; **Секции**; **Предупреждения разбора**.

Как читать: «фактический шаг» ≠ `interval` или разрывы > 1.5×interval — хост зависал или nmon перезапускали.
`TOP: нет` — nmon запущен без `-t`, анализа процессов не будет. `UARG: нет` — без `-T`, флаги JVM недоступны.

### `check` — качество данных
Перекрёстные проверки (сумма CPU_ALL ≈ 100 %; число CPU по трём источникам; среднее busy ядер ≈ CPU_ALL;
`VM pgpgout ≈ Σ DISKWRITE×interval`; `pgpgin ≈ Σ DISKREAD×interval`; трафик bond ≈ сумме слейвов; средний размер
IO; постоянство memtotal; MEM ≈ /proc/meminfo; покрытие TOP; `Σ TOP MajorFault × interval` vs `VM pgmajfault` —
если отношение ≫ 1, колонка MajorFault в TOP для этого файла ненадёжна; оценка avail vs MemAvailable ядра на
старте), список «мёртвых» колонок (всегда 0 / всегда N/A),
замечания (нераспознанные строки, неизвестные секции, AIX-секции, отсутствие ZZZZ, план снимков vs факт,
дрожание шага > 25 %, движение времени назад между соседними строками ZZZZ в порядке файла — снимки при этом
переупорядочиваются по времени, разрывы) и **вердикт**: пригодны / с оговорками / непригодны.

### `report` — сводный отчёт по хосту
**Ключевые показатели** (период, CPU/RAM, ОС, CPU busy avg/p95/max с временем, user/sys/wait/steal, макс. ядро
без первых снимков файлов, Runnable/Blocked, память used/avail (с калибровкой по MemAvailable)/page cache без
shmem/swap, swap-out, major faults, активность kswapd (pageoutrun), счётчики direct reclaim/kswapd_steal — с
пометкой `n/a`, если ядро их не отдаёт, диски (busy,
пики записи и чтения), сеть, ФС ≥ 70 %, процессы java (CPU, RSS, потоки), процессы по суммарному CPU);
**Замечания (health)**; **Таймлайн** с шагом 5/15/60 мин в зависимости от длины периода (для загрузок — max в
корзине, для памяти — среднее; границы корзин кратны шагу от полуночи). Начинайте анализ хоста с этой команды.

### `health` — только замечания
Итог по числу CRIT/WARN/INFO и список замечаний в формате:

```
[CRIT] DISK_BUSY @ 2026-03-14 03:00:08: busy p95 nvme0n1 (/opt/ignite/db) = 98.7 (порог ≥ 80.0)
    факты: avg 47%, max 100% @ 2026-03-14 03:00:08; write max 177505 KB/s, read max 165081 KB/s
    подсказка: диск загружен: checkpoint/WAL/rebalance/снапшот; ...
```

Коды и пороги — раздел 6. Код возврата: 2 при CRIT, 1 при WARN, 0 иначе.

### `cpu` — загрузка процессора
Сводка CPU_ALL (avg/median/p95/max с временем/min для busy, user, sys, wait, idle, steal); время выше порогов
busy 50/70/80/90/95 % и wait 5/10/25 %; топ пиков busy с разложением и топ-процессом снимка; эпизоды
насыщения (busy > 80 % ≥ 2 снимка подряд) и эпизоды iowait > 10 %; блок **Ядра**: число ядер, CV средних по
ядрам, «максимальное ядро» avg/p95/max с временем, число снимков с ядром > 90 % и, отдельно, с ядром > 90 % при
общей загрузке < 50 % (однопоточное узкое место); самые загруженные ядра; ядра с наибольшим iowait; busy в
«ядрах». Статистика по ядрам считается **без первого снимка каждого файла** (T0001 охватывает неполный интервал
и часто показывает ложные 100 % на одном ядре).

Интерпретация: `busy` = User + Sys (steal не входит). На узле с 56 CPU общая загрузка 15 % может скрывать одно
ядро на 100 % — это видно только в блоке «Ядра». `wait` (iowait) — CPU простаивал, пока были незавершённые
операции ввода-вывода; при высокой загрузке CPU iowait занижается. `steal` > 0 бывает только в виртуальных
машинах и означает, что гипервизор отбирает время.

### `cores` — таблица по каждому логическому CPU
Опции: `--sort avg|p95|max|sys|wait`, `--top N`. Колонки: avg/p95/max busy, avg user/sys/wait, max steal, время > 90 %
(все — без первого снимка каждого файла, как и в `cpu`).
Дополнительно: топология из lscpu, почти неиспользуемые ядра (avg < 1 %, признак cpuset/isolcpus/IRQ-only),
загрузка по NUMA-узлам (если узлов > 1), физические ядра по /proc/cpuinfo и сколько физических ядер имели оба
HT-потока > 80 % одновременно. Нумерация nmon `CPU001` = CPU 0 в ОС.

### `proc` — планировщик
Runnable (очередь на выполнение, мгновенное значение в момент снимка), Blocked (процессы/потоки в D-state,
ждут ввода-вывода), pswitch/s, fork/s; время, когда Runnable > 1×CPU и > 2×CPU, Blocked > 1/5/20; пики Blocked
с iowait, самым занятым диском и топ-процессом. Колонки syscall/read/write/exec/sem/msg на Linux всегда −1
(nmon их не собирает) и скрываются.

### `mem` — память
Сводка MEM (начало/avg/min с временем/max с временем/конец/% от total) для memfree, cached, buffers, used,
avail, active, inactive, memshared, swap used, swapcached; тренды (наклон MB/ч, r², «конец − начало» — разница
последнего и первого значений, время до исчерпания — только при r² ≥ 0.7); момент минимума доступной памяти с
контекстом (reclaim-счётчики,
топ-процесс); память вне видимых процессов (used − Σ RSS из TOP, плюс Σ ShdLib); /proc/meminfo на старте nmon.
В JSON значения таблиц и kv-блоков — числа (MB; для meminfo — KB); в text/md они печатаются в удобных единицах.

Определения: `used = memtotal − memfree − cached − buffers` (как `used` у `free`); `avail ≈ memfree + buffers +
(cached − memshared) + slab reclaimable` — приближение MemAvailable (в nmon MemAvailable нет; `memshared` =
Shmem/tmpfs входит в `cached`, но не вытесняется, поэтому вычитается). Точное MemAvailable ядра на момент старта
есть в блоке meminfo и печатается рядом для калибровки: оценка обычно выше на 20–40 %, так как ядро дополнительно
резервирует watermarks и считает вытесняемой лишь часть page cache. r² близко к 1 при положительном наклоне =
устойчивый рост (утечка/накопление); низкое r² = колебания. Отрицательное «used − Σ RSS» — норма, когда в RSS
процесса много file/shmem-страниц (колонка ShdLib), которые nmon учитывает в `cached`, а не в `used`.

### `vm` — подкачка, reclaim, page faults, грязные страницы
Сводка по счётчикам VM: pgpgin/pgpgout (KB/s), pswpin/pswpout (страниц за интервал), pgfault/pgmajfault (/s),
kswapd_steal, pgscan_kswapd, pgscan_direct, pgsteal, allocstall, pageoutrun, slabs_scanned, pgdeactivate,
pgactivate (за интервал), nr_dirty/nr_writeback/nr_mapped/nr_slab/nr_page_table (MB, текущие значения); блок
грязных страниц (max dirty, время сброса при средней скорости записи, nr_writeback); признаки давления на
память (swap-активность, reclaim, kswapd0 в TOP); замечание о «мёртвых» счётчиках ядра.

**Важно:** на современных ядрах Linux колонки `kswapd_steal`, `pgsteal_*` (переименованы с ядра 3.4),
`pgscan_kswapd_*`, `pgscan_direct_*`, `pgrefill_*` (с 4.8), `allocstall` (с 4.10) в nmon **всегда 0**: имена
счётчиков в `/proc/vmstat` изменились, nmon читает старые. На RHEL/CentOS 7 (ядро 3.10) `allocstall` и
`pgscan_*_normal` ещё работают; на RHEL 8/9 и производных, Ubuntu 18+ — нет. Не делайте из их нулей вывод
«reclaim не было». Признаки reclaim на современных ядрах: `pageoutrun > 0` (kswapd просыпался),
`slabs_scanned > 0`, рост `pgdeactivate`, процесс `kswapd0` в TOP с заметным CPU, memfree у нижней границы.
Прямой reclaim (allocstall) на ядрах ≥ 4.10 в nmon не виден вообще.

### `disk` — блочные устройства
Опции: `--dev REGEX` (полное совпадение по имени устройства или имени LV, можно несколько), `--all`
(включая разделы и dm-*), `--top N`. По умолчанию показываются **физические** устройства (без разделов и
dm-*, чтобы не считать трафик дважды: запись в LV проходит и через dm-N, и через физический диск).

Таблица: устройство (для dm-N в скобках имя LV), mount (для физического диска без своей ФС — точки монтирования
его LV/разделов), busy avg/p95/max с временем, время > 80 %, read/write avg/max KB/s, IOPS avg/max, средний размер
IO (KB, = Σ(read+write)/Σ IOPS — взвешенно по операциям, простои не занижают), `svc≈ms` (оценка времени на
операцию = util×10/IOPS, медиана по снимкам с IOPS ≥ 10), `stalled` (снимков с busy ≥ 95 % при IOPS < 1 —
устройство «висит»), прочитано/записано всего. Итого по физическим дискам; пики записи и чтения по каждому
устройству с busy, размером IO и топ-процессом (первые снимки файлов T0001 исключены); **периодичность
всплесков**: интервалы между локальными пиками ≥ p90 — период считается установленным («всплески регулярны»),
только если интервалов ≥ 8, период ≥ 3 шагов nmon и ≥ 60 % интервалов лежат в пределах max(±25 %, ±1 шаг) от
медианы (фактический допуск печатается в секундах); иначе печатается «пики нерегулярны» с медианным
интервалом и разбросом. Регулярный период ≈ 180 с — типичная сигнатура checkpoint Ignite (`checkpointFrequency`
по умолчанию 180 с), но при интервале nmon 60 с трёхминутный цикл находится на пределе разрешения: для
уверенной детекции нужен интервал ≤ 30 с. Таблица времени обслуживания — если в файле есть
DISKREADSERV/DISKWRITESERV. `--dev` сопоставляется с именем устройства (`dm-4`), с именем из /dev/mapper
(`vg-lv`, как в колонке LV команды `diskmap`) и с именем LV без группы томов (`lv`).

Интерпретация busy: доля времени, когда у устройства была хотя бы одна операция в очереди (util). Для HDD/SAS
busy ≈ 100 % — реальный предел; для NVMe и RAID с параллелизмом 100 % достигается задолго до предела
пропускной способности, поэтому смотрите ещё IOPS, размер IO, Blocked и iowait. Маленький средний IO (4–8 KB)
при высоком busy = случайные/синхронные записи (WAL fsync, страницы checkpoint); большой (≥ 64 KB) =
последовательные (архив WAL, снапшот, бэкап).

### `diskmap` — карта хранилища
Устройство nmon → тип → размер → **физический диск** (корень дерева lsblk) → родитель → LV → точка
монтирования (для диска без своей ФС — точки монтирования потомков) → fs → use % на старте → опции монтирования
(из дерева lsblk, `ls -l /dev/mapper`, /proc/partitions, mount, df -m в BBBP); `df -m` на старте; точки
монтирования, похожие по именам на хранилище Ignite (ignite/wal/persist/snapshot/archive/db/data) с указанием
физического диска — так видно, делят ли WAL, persistence и архив один диск; `/proc/diskstats` на
старте — накопительно с загрузки ОС: число операций, средняя латентность ms/операцию (включая очередь),
средний размер IO, объёмы, util с загрузки, in_flight. По латентности с загрузки легко отличить HDD/SAS
(> 5 ms) от SSD/NVMe (< 1 ms). Используйте эту команду, чтобы понять, какой физический диск стоит за
каталогами persistence/WAL/архива/снапшотов/логов.

### `fs` — заполненность файловых систем
Опции: `--mount REGEX`. Для каждой точки монтирования (JFSFILE): размер (из df), % в начале/конце/min/max с
временем, Δ за период, рост п.п./ч и r² (регрессия), рост MB/ч, время до 100 % при текущем росте (печатается
только при r² ≥ 0.7 и росте ≥ 0.05 п.п./ч, иначе `-`), свободно в конце; скачки ≥ 2 п.п. за интервал
(удаление/ротация/создание снапшота); JFSINODE, если есть. Псевдо-ФС (tmpfs, devtmpfs, /dev, /run, /sys)
скрыты — укажите их явно через `--mount`. Разрешение JFSFILE — 0.1 %, на больших ФС один шаг = гигабайты,
поэтому оценка роста — линейная экстраполяция.

### `net` — сеть
Опции: `--iface REGEX`, `--all` (показать интерфейсы без трафика), `--link-mbit N`. Таблица интерфейсов: роль
(bond / bond-slave / nic / lo; по флагам MASTER/SLAVE из ifconfig, а если ifconfig в BBBP нет — слейвы
определяются по трафику: набор NIC, суммарный трафик которых совпадает с трафиком бонда, и помечаются «по
трафику»), MTU, rx/tx avg/p95/max KB/s с временем максимума, пакеты/с, средний размер пакета (байт; маленький
~100–500 B = много мелких сообщений/RPC, большой ~ MTU = массовая передача: rebalance, снапшот, putAll), объёмы за
период; итог по хосту (без lo и bond-слейвов, чтобы не удваивать) и % использования линка при `--link-mbit`
(ёмкость линка переводится в KiB/s, как считает nmon); пики суммарного трафика с sys % и топ-процессом; отрезки
нулевого трафика на активном интерфейсе (возможная изоляция узла); счётчики интерфейсов на старте (ifconfig, а
без него — /proc/net/dev) с накопительными ошибками и дропами; NETERROR, если есть.

### `top` — процессы (секция TOP)
Опции: `--pid N` (несколько раз), `--cmd REGEX`, `--by-cmd` (сгруппировать все PID одной команды),
`--sort cpu|cpumax|rss|threads|majflt|sys|snapshots`, `--top N` (по умолчанию 20). Колонки: команда, pid,
снимков (в скольких снимках процесс попал в TOP), впервые/последний раз, cpu avg/p95/max с временем, доля sys,
RSS начало/max/конец (MB), threads начало/max/конец, major faults avg/max в секунду, minor faults avg в секунду,
сумма IOwaitTime. Дополнительно: учёт CPU (сумма %CPU процессов в пересчёте на все CPU vs CPU_ALL busy —
неучтённая доля = мелкие процессы ниже порога TOP, прерывания, kernel-потоки) и смена PID у команды `java`
(перезапуск: PID исчез до конца данных, и после этого впервые появился новый PID той же команды, не
существовавший одновременно со старым; одновременно работающие JVM перезапуском не считаются).

**Порог TOP:** nmon пишет в TOP только процессы, потреблявшие заметный CPU в интервале, и начиная с T0002.
Отсутствие процесса в снимке ≠ он не работал (он мог быть idle). `%CPU` — в процентах **одного** ядра: 560 %
= 5.6 ядра; на 56 CPU это 10 % машины. `MinorFault`/`MajorFault` — события **в секунду** (nmon делит приращение
на длину интервала). `IOwaitTime` учитывает только главный поток процесса и для многопоточных JVM неинформативен.

### `java` — JVM (Ignite) глазами ОС
Для каждого процесса `java`: pid, доля снимков присутствия и период, %CPU avg/p95/max (в ядрах и в % машины),
время максимума, доля sys в CPU процесса, RSS начало/max/конец и % от RAM, **анонимная RSS** (ResSet − ShdLib —
без file/shmem-страниц, ближе к реальному потреблению) и её % от RAM, file/shmem-часть RSS, тренд RSS (MB/ч,
r²), VSZ, threads начало/max/конец и тренд, major/minor faults в секунду (с автоматической сверкой MajorFault
процесса с системным `VM pgmajfault`: если расхождение более чем в 10 раз, значение TOP помечается как
ненадёжное), IOwaitTime (только главный поток — для JVM неинформативно); снимки с CPU < 10 % от медианы
(возможные паузы/остановки); пропуски присутствия в TOP; пики %CPU с контекстом (sys, CPU_ALL, iowait, RSS,
threads, majflt/s); перезапуски (смена PID по времени жизни каждого PID, простой между, RSS нового и старого
процесса — маленький RSS нового = «холодный» старт); другие процессы с заметным CPU с категорией (мониторинг,
антивирус, бэкап, kernel reclaim/writeback, JVM-утилиты…); при наличии UARG — роль JVM, флаги и оценка памяти
по флагам (Xmx + MaxDirectMemorySize + стеки потоков vs RSS → сколько приходится на off-heap Ignite/metaspace).

Интерпретация: RSS JVM Ignite = heap + off-heap data regions + checkpoint buffer + metaspace + стеки потоков +
буферы + file/shmem-страницы (mmap, tmpfs); рост RSS до суммы настроенных регионов после старта — норма, рост
после плато — повод искать утечку. Высокая доля sys (> 30 %) — page faults (первое касание памяти без
AlwaysPreTouch, THP), futex-конкуренция, сетевой ввод-вывод. GC-паузы nmon не видит; косвенный признак — провал
%CPU при том, что узел не был занят.

### `uarg` — командные строки и флаги JVM (нужен nmon `-T`)
Опции: `--cmd REGEX`, `--full`. Список процессов с командными строками; для java — роль (серверный узел Ignite
по `CommandLineStartup`, ZooKeeper, control.sh, JVM с Ignite в classpath), извлечённые флаги: Xms/Xmx/Xmn/Xss,
MaxDirectMemorySize, MaxMetaspaceSize, тип GC, MaxGCPauseMillis, ParallelGCThreads/ConcGCThreads,
AlwaysPreTouch, UseLargePages, UseTransparentHugePages, HeapDumpOnOutOfMemoryError,
ExitOnOutOfMemoryError, DisableExplicitGC, GC-лог, JMX-порт, все `-DIGNITE_*`, все `-XX:*`; оценка памяти
по флагам. Без `-T` секции UARG нет — команда сообщит об этом.

### `at` — срез в момент времени
Опции: `--time T` (по умолчанию — момент максимальной загрузки CPU), `--window-snaps K` (снимков до/после,
по умолчанию 2; `0` — только сам снимок), `--metrics ...`, `--top N`. Выводит: ближайший снимок и его id
`Tnnnn`, таблицу ключевых метрик для K снимков вокруг момента, TOP-процессы в этот снимок, все устройства с
busy ≥ 1 % (включая разделы и dm-*), сеть, ядра с busy > 90 %. Если запрошенный момент лежит вне периода данных (дальше 1.5 интервала от ближайшего
снимка), печатается строка «ВНИМАНИЕ» и предупреждение в stderr — проверьте дату и часовой пояс. Это основная
команда для вопроса «что происходило в 03:52 по логу Ignite».

### `timeline` — временной ряд метрик
Опции: `--metrics имена...` (по умолчанию набор из cpu/proc/mem/disk/net/java), `--step 5m` (укрупнение;
границы корзин кратны шагу от полуночи), `--agg mean|max|min|sum|last` (агрегат в корзине; для загрузок
берите `max`, чтобы не терять пики), `--limit N`. Заголовки колонок содержат единицы. Неизвестные имена метрик
пропускаются с предупреждением `WARN:` в stderr (во всех командах с `--metrics`). Снимки без данных секции
(например, обрезанная строка NET) остаются пустыми (`-`), а не считаются нулём. Удобно с
`--around`/`--from`/`--to` и `--format csv`.

### `events` — выбросы во времени
Опции: `--metrics ...`, `--z 4` (порог робастного z-score; `--z 0` снимает порог по z, но минимальные
абсолютные отклонения по-прежнему отсекают шум), `--window-snaps 15` (окно скользящей медианы), `--limit`.
Для каждой метрики выброс = отклонение от медианы соседних снимков более чем на z×MAD и больше минимального
абсолютного порога (например, для cpu.busy ≥ 10 п.п., для disk.write ≥ 20 MB/s). Первые снимки файлов (T0001)
событиями не считаются.
Для `mem.free` ищутся провалы, для `top.java.cpu`/`top.java.threads` — отклонения в обе стороны. Второй блок —
моменты, когда выбросы случились сразу по ≥ 3 метрикам (наиболее вероятные «события»).

### `correlate` — корреляции Пирсона
Опции: `--metrics ...`, `--target M` (корреляции только с одной метрикой), `--limit`. Без `--target` — пары
с |r| ≥ 0.5. Типичные полезные связи: `disk.write ↔ cpu.wait ↔ proc.blocked` (запись тормозит узел),
`net.read ↔ disk.write` (узел принимает данные rebalance/снапшота и пишет их), `cpu.sys ↔ net.*` (softirq),
`vm.pgmajfault ↔ disk.read` (память вытеснена, читаем с диска). Корреляция ≠ причинность.

### `compare` — два окна времени
Опции: `--a 'HH:MM-HH:MM'`, `--b 'HH:MM-HH:MM'` (или `'начало..конец'` в любом формате времени), `--metrics`,
`--top`. Таблица avg/p95/max в A и B и Δ % (отсортирована по |Δavg|), плюс процессы с изменившимся средним
CPU (среднее по всем снимкам окна: отсутствие процесса в TOP считается как 0 %; рядом — в скольких снимках он
попал в TOP). Типовое использование: окно «до инцидента» против окна «во время».

### `cluster` — сравнение хостов
Опции: `--sort метрика:агрегат` (только колонки таблицы, например `cpu.busy:p95`; неизвестная колонка —
ошибка со списком допустимых), `--metrics` (для поиска синхронных выбросов), `--z`. Блоки: покрытие данными
(начало/конец/длительность/снимки/CPU/RAM/разрывы/файлы), объединённое и общее окно, полоса покрытия по
времени (`#` — есть данные), различия конфигурации (CPU, RAM, ядро, версия nmon, interval, MTU, swap, THP,
флаги JVM, модель CPU), таблица метрик по хостам (mean/p95/max/min за период), выбросы (робастный z по
медиане/MAD с требованием отличия ≥ 10 %, только при ≥ 4 хостах; если покрытие хостов различается более чем в
1.5 раза, агрегаты для выбросов считаются в общем окне всех хостов, о чём сказано в примечании — иначе
длинные файлы с другой фазой нагрузки выглядели бы «выбросами»; если отклоняется > 25 % хостов, метрика
показывается как «узлы делятся на группы»), синхронные выбросы (корзина времени, число и доля хостов —
только когда выброс есть минимум у двух хостов, **первый хост** по точному времени), кластерный таймлайн
(границы корзин кратны шагу; для каждого хоста берётся среднее по его снимкам в корзине; mean cpu по хостам, max
blocked/busy, суммы disk/net/java по хостам, у которых метрика есть), неполное покрытие (хост закончился раньше
других = вероятное падение узла), замечания уровня кластера, health по хостам (число CRIT/WARN и коды). Код
возврата учитывает и кластерные замечания, и health по хостам.

### `export` — выгрузка данных
Опции: `--section NAME` (`CPU_ALL`, `MEM`, `DISKWRITE`, `JFSFILE`, `TOP`, `UARG`, …) с `--columns REGEX...`,
либо `--metrics имена...` с `--step`/`--agg`; `--limit N` ограничивает число строк. Все строки получают
реальную метку времени. С `--format csv`
удобно для собственного скрипта агента; `--format json` даёт строки как объекты, ключ = имя колонки.

### `bbbp` — конфигурационные блоки
Опции: `--block REGEX` (`lscpu`, `/proc/meminfo`, `/bin/df-m`, `/bin/mount`, `/etc/fstab`, `ifconfig`,
`netstat -r`, `/proc/diskstats`, `/proc/partitions`, `/proc/modules`, `/etc/release`, `uptime`…),
`--grep REGEX` (по строкам всех блоков), `--limit`. Без опций — список блоков с числом строк.

### `sections` и `metrics`
`sections` — какие секции есть, число колонок и значений, единицы, первые колонки, блоки BBBP.
`metrics` — все доступные имена метрик для данного файла (см. раздел 5) с единицами.

## 5. Имена метрик

Используются в `timeline`, `events`, `correlate`, `compare`, `export --metrics`, `at --metrics`, `cluster --metrics`.

| Имя | Единица | Смысл |
|---|---|---|
| `cpu.busy` | % | User + Sys по CPU_ALL (в % от всех CPU) |
| `cpu.user`, `cpu.sys`, `cpu.wait`, `cpu.idle`, `cpu.steal` | % | колонки CPU_ALL |
| `cpu.core_max` | % | максимальная busy среди ядер в снимке |
| `cpu.hot_cores` | шт. | число ядер с busy > 90 % |
| `cpu.core<N>.<поле>`, поле = busy, user, sys, wait, idle, steal | % | конкретное ядро, N — номер как в nmon (с 1) |
| `proc.runq`, `proc.blocked` | шт. | Runnable, Blocked |
| `proc.pswitch`, `proc.fork` | /s | переключения контекста, fork |
| `mem.free`, `mem.cached`, `mem.buffers`, `mem.active`, `mem.inactive`, `mem.shared`, `mem.swapcached` | MB | колонки MEM |
| `mem.used` | MB | total − free − cached − buffers |
| `mem.avail` | MB | оценка MemAvailable: free + buffers + (cached − shmem) + slab reclaimable (см. раздел 4, `mem`) |
| `mem.swap_used` | MB | swaptotal − swapfree |
| `vm.pgpgin`, `vm.pgpgout` | KB/s | обмен с блочными устройствами |
| `vm.pswpin`, `vm.pswpout` | страниц/интервал | подкачка |
| `vm.pgfault`, `vm.pgmajfault`, `vm.pgfree` | /s | page faults |
| `vm.kswapd_steal`, `vm.pgscan_kswapd`, `vm.pgscan_direct`, `vm.pgsteal`, `vm.allocstall` | /интервал | reclaim (на ядрах ≥ 4.x всегда 0 — см. раздел 9) |
| `vm.pageoutrun`, `vm.slabs_scanned`, `vm.pgdeactivate`, `vm.pgactivate` | /интервал | reclaim-активность, работающая на современных ядрах |
| `vm.nr_dirty`, `vm.nr_writeback`, `vm.nr_mapped`, `vm.nr_slab`, `vm.nr_page_table` | MB | текущие значения (страницы × 4 KB) |
| `disk.busy_max` | % | максимальная busy среди всех устройств |
| `disk.read`, `disk.write` | KB/s | сумма по физическим дискам |
| `disk.iops` | /s | сумма IOPS по физическим дискам |
| `disk.<dev>.<поле>`, поле = busy, read, write, iops (синоним xfer), bsize, rserv, wserv | %, KB/s, /s, KB, ms | конкретное устройство (`sda`, `nvme0n1`, `dm-3`) |
| `net.read`, `net.write` | KB/s | сумма по интерфейсам без lo и bond-слейвов |
| `net.<if>.<поле>`, поле = read, write, pkt_in, pkt_out | KB/s, pkt/s | конкретный интерфейс |
| `fs.<mount>.pct`, `fs.<mount>.inode` | % | заполненность точки монтирования по месту / по inode (например `fs./opt/ignite.pct`) |
| `top.java.cpu`, `top.java.usr`, `top.java.sys` | % одного ядра | сумма по всем процессам java |
| `top.java.rss`, `top.java.vsz` | MB | RSS / VSZ java |
| `top.java.threads` | шт. | потоки java |
| `top.java.majflt`, `top.java.minflt` | /s | page faults java в секунду; `majflt` из TOP сверяйте с `vm.pgmajfault` (см. раздел 9) |
| `top.java.iowait` | ticks | IOwaitTime java (только главный поток — для JVM неинформативно) |
| `top.sum_cpu` | % одного ядра | сумма %CPU всех процессов TOP |
| `top.kswapd.cpu` | % | CPU процесса kswapd |
| `top.<cmd>.<поле>`, `top.pid<PID>.<поле>`, поле = cpu, usr, sys, rss, vsz, threads, majflt, minflt, iowait | как у top.java.* | любой процесс по имени (префикс) или PID |
| `raw.<SECTION>.<column>` | как в секции | любая колонка любой секции (например `raw.VM.pgrotated`, `raw.NETPACKET.bond0-read/s`) |

Метрики TOP равны NaN в снимках, где процесс не попал в TOP.

## 6. Правила health: коды, пороги, смысл

Формат порога: `WARN / CRIT`. «↓» — хуже, когда значение меньше. Переопределение: `--thr CODE=WARN[,CRIT]`.

| Код | Что измеряется | WARN / CRIT | Что обычно означает для Ignite |
|---|---|---|---|

## 8. Форматы вывода, JSON, коды возврата

- `text` (по умолчанию): заголовок `=== <отчёт> [host] ===`, блоки `--- <название> ---`, таблицы с выровненными
  колонками, `(показано N из M)` при усечении, `(примечание)` под блоком.
- `md`: те же блоки в Markdown (`# / ##`, таблицы `| … |`).
- `json`: массив отчётов (один на хост; для `cluster` — один отчёт):

```json
[{"title": "…", "host": "node01",
  "blocks": [
    {"type": "kv", "title": "…", "items": {"ключ": "значение"}, "note": null},
    {"type": "table", "title": "…", "columns": ["a", "b"], "rows": [{"a": 1, "b": "x"}], "note": null, "total_rows": 10},
    {"type": "text", "title": "…", "text": "…"},
    {"type": "findings", "title": "…", "items": [
       {"severity": "CRIT", "code": "DISK_BUSY", "host": "node01", "time": "2026-03-14 03:00:08",
        "metric": "busy p95 nvme0n1 (/opt/ignite/db)", "value": 98.7, "threshold": "≥ 80.0",
        "evidence": "…", "hint": "…"}]}]}]
```
  NaN/inf сериализуются как `null`, времена — строки `YYYY-MM-DD HH:MM:SS`.
- `csv`: только табличные блоки (несколько таблиц разделяются пустой строкой); NaN → пустая ячейка.
- Коды возврата: `0` — успех; для `health`, `report`, `cluster` — `1`, если есть WARN, `2`, если есть CRIT
  (для `cluster` учитываются и кластерные замечания, и health по каждому хосту; удобно в скриптах); `1` с
  сообщением `ERROR: …` в stderr при ошибках данных/аргументов (неверное время, длительность, окно, колонка
  сортировки, неизвестный код правила), `2` при ошибке синтаксиса argparse. Предупреждения печатаются в stderr с
  префиксом `WARN:` и не мешают выводу.
- Вывод детерминирован: одинаковые входные данные и аргументы дают одинаковый текст.

## 9. Семантика данных nmon (что нужно знать, чтобы не ошибиться)

- **Время.** Метка снимка `ZZZZ` — момент завершения интервала; значения секций — средние за
  предшествующий интервал (`AAA,interval`, обычно 60 с). Время — локальное время хоста без зоны. Первый
  снимок `T0001` охватывает неполный интервал; TOP начинается с `T0002`. Сравнение с логами в другой зоне —
  через `--tz-shift`.
- **CPU_ALL** — проценты от всех логических CPU; `Busy` пустая (не считается nmon); `Steal%` есть у nmon ≥ 14.
  `CPUnnn` — по каждому логическому CPU, нумерация с 1 (CPU001 = cpu0).
- **MEM** — в MB. `cached` включает tmpfs/shmem (`memshared`, он же `Shmem` в meminfo), которые не
  вытесняются, поэтому скрипт считает `avail ≈ memfree + buffers + (cached − memshared) + slab reclaimable`; это
  всё равно выше MemAvailable ядра на 20–40 % (ядро учитывает watermarks и лишь часть page cache) — точное
  значение на старте есть в meminfo. `-0.0`/`-1.0` = не поддерживается.
- **VM** — первые шесть `nr_*` — текущие значения в страницах (скрипт переводит в MB по 4 KB); остальные —
  **приращения за интервал** (не за секунду): `pgpgin/pgpgout` в KB за интервал (скрипт делит на интервал →
  KB/s, и это совпадает с суммой DISKREAD/DISKWRITE физических дисков), `pgfault/pgmajfault` — события за
  интервал (скрипт даёт /s), `pswpin/pswpout` — страницы за интервал. На ядрах ≥ 3.x/4.x счётчики
  `kswapd_steal`, `allocstall`, `pgscan_*`, `pgsteal_*`, `pgrefill_*`, `pgalloc_high/dma`, `pginodesteal`,
  `nr_unstable` всегда 0 (переименованы в /proc/vmstat: `kswapd_steal`/`pgsteal_*` — с ядра 3.4,
  `pgscan_*_normal`/`pgrefill_*` — с 4.8, `allocstall` — с 4.10; на RHEL/CentOS 7 с ядром 3.10 `allocstall` и
  `pgscan_*_normal` ещё работают). `report` помечает такие нули как `n/a` с учётом версии ядра из AAA,OS.
- **PROC** — `Runnable`/`Blocked` — мгновенные значения (`procs_running`/`procs_blocked`) в момент снимка, не
  средние; `pswitch`/`fork` — в секунду; `syscall/read/write/exec/sem/msg` = −1 на Linux.
- **DISK*** — по всем блочным устройствам, включая разделы и dm-N (LVM): один и тот же ввод-вывод учитывается на
  физическом диске, его разделе и на dm-устройстве. Скрипт суммирует только физические устройства; для
  LV смотрите `--dev`/`--all`. `DISKBUSY` = util; `DISKXFER` = IOPS (чтение+запись вместе); `DISKBSIZE` =
  средний KB на операцию. Устройств больше `disks_per_line` (150) — nmon делит секции на DISKBUSY1…; скрипт
  склеивает. Латентность (DISKREADSERV/DISKWRITESERV) в типичных файлах nmon для Linux отсутствует.
- **JFSFILE** — % занятости с шагом 0.1 %; абсолютные размеры берутся из `df -m` на старте (BBBP).
- **NET/NETPACKET** — KB/s и пакеты/с по каждому интерфейсу; трафик bond дублируется на его слейвах
  (скрипт исключает слейвы и lo из сумм). Ошибки/дропы — только накопительно на старте (ifconfig,
  /proc/net/dev), если нет секции NETERROR.
- **TOP** — только процессы с заметным CPU в интервале; `%CPU` — в процентах одного ядра (может быть > 100);
  `Size` (VSZ), `ResSet` (RSS), `ResText`, `ResData`, `ShdLib` (file/shmem-backed часть RSS) — в KB;
  `MinorFault/MajorFault` — события **в секунду** (nmon делит приращение счётчиков процесса на длину интервала);
  `MajorFault` у JVM в некоторых файлах на порядки превышает системный `VM pgmajfault` за те же интервалы —
  скрипт сверяет их (`check`, `java`) и помечает колонку как ненадёжную; для выводов о major faults используйте
  `vm.pgmajfault`. `Threads`, `IOwaitTime` — только в nmon ≥ 16; `IOwaitTime` берётся из /proc/PID/stat главного
  потока и для многопоточных JVM остаётся 0 даже при реальном ожидании I/O. Имя команды обрезано до 15
  символов (comm). Нет PPID/UID/состояния процесса.
- **UARG** — только при запуске nmon с `-T`; содержит полную командную строку (флаги JVM).
- **BBBP** — однократный снимок конфигурации в момент старта nmon (lscpu, meminfo, df, mount, fstab, lsblk,
  ifconfig, diskstats, uptime…). Изменения во время записи не видны.
- **Объединение файлов хоста** — по имени хоста из `AAA,host`; снимки с одинаковым временем (±полинтервала)
  дедуплицируются; метаданные и BBBP берутся из самого раннего файла.

## 10. Сценарии разбора инцидентов Ignite

Ниже — какие сигнатуры искать в nmon и какими командами. Во всех случаях итоговый вывод о причине делается
вместе с логами Ignite (`Checkpoint started/finished`, `Too many dirty pages`, `Long JVM pause`,
`Node FAILED/LEFT`, `Local node SEGMENTED`, PME/rebalance-сообщения) и GC-логами.

### 10.1. Долгие checkpoint, write throttling, «узел тормозит каждые N минут»
Сигнатуры: пики `disk.write` на диске persistence, регулярные с периодом ≈ `checkpointFrequency`
(`CHECKPOINT_PERIOD` — при интервале nmon 60 с трёхминутный цикл может не распознаваться как регулярный, тогда
смотрите таблицу пиков глазами), во время пиков `disk.busy_max` ≈ 100 %, `proc.blocked` ↑, `cpu.wait` ↑,
`top.java.cpu` проваливается или растёт sys-доля (`IO_STALL`, `BLOCKED_HIGH`, `CPU_WAIT`), `vm.nr_dirty`
растёт перед сбросом. Команды: `health`, `disk` (пики и периодичность, размер IO), `timeline node01.nmon
--metrics disk.write disk.busy_max proc.blocked cpu.wait top.java.cpu vm.nr_dirty`, `correlate --target
proc.blocked`, `at --time <момент из лога>`.
Уточнение: если пики записи идут на диск с большим средним IO и высоким svc≈ms — диск не тянет; если IO мелкий
при огромном IOPS — много случайных страниц (маленький checkpoint buffer, большие data regions на медленном
диске). Проверьте `diskmap`: не делят ли WAL, persistence и архив один физический диск.

### 10.2. Узел выпал из топологии / segmentation / failure detection
Сигнатуры на пострадавшем узле: `NMON_GAP` (nmon сам не смог снять данные — хост «замер»), `JAVA_CPU_DROP` /
`JAVA_ABSENT`, `NET_ZERO` на bond/NIC, `CPU_STEAL` (в VM), `SWAP_ACTIVITY`, `CPU_SATURATION` + `RUNQ_HIGH`
(потоки discovery не получают CPU). На остальных узлах: синхронный всплеск `top.java.cpu`/`net.*` в момент
PME (`CLUSTER_SYNC`), затем rebalance (10.4). Команды: `cluster` (покрытие: узел, закончивший данные раньше;
синхронные выбросы с «первым хостом»), `check` (разрывы), `java`, `net`, `at --time <момент FAILED> <dir>`.
Оговорка: nmon не различает «узел замер сам» и «его исключили»; порядок событий между хостами надёжен только
при синхронных часах и с точностью до интервала.

### 10.3. OOM-killer / перезапуск JVM / рост памяти
Сигнатуры: `JAVA_RESTART` (смена PID; RSS нового процесса мал), перед этим `MEM_AVAIL_LOW`, `JAVA_RSS` ≥ 90 %
(по анонимной RSS), `KSWAPD_ACTIVE` и `MEM_FREE_LOW` на уровне WARN (то есть с подтверждением давления),
`MAJFAULT_HIGH` (по системному `vm.pgmajfault`, не по TOP), сжатие `mem.cached`, иногда `SWAP_*`. Рост после
плато: `JAVA_RSS_GROWTH`, `MEM_GROWTH`, `JAVA_THREADS_GROWTH`. Команды: `java`, `mem`, `vm`, `timeline
node01.nmon --metrics top.java.rss mem.free mem.cached vm.pgmajfault`, `uarg` (Xmx, MaxDirectMemorySize —
сравните сумму с RSS и с размерами data regions из конфигурации). nmon не видит сам факт OOM-kill —
подтверждайте по dmesg/journal и логам Ignite.

### 10.4. Rebalance / снапшот / массовая загрузка / бэкап
Сигнатуры: всплески `net.read` (принимающие узлы) и `net.write` (отдающие), крупный средний пакет (~MTU),
`disk.read` на persistence у отдающих и `disk.write` у принимающих, рост `top.java.cpu`; при снапшоте —
последовательная запись (большой IO) на архивный/снапшотный том и рост `fs.<mount>.pct`; при бэкапе — процесс
из категории «бэкап/копирование» в `java` (другие процессы). Команды: `cluster` (кластерный таймлайн:
суммарные disk/net; синхронные выбросы), `net`, `disk --all`, `fs`, `correlate --target net.read`.

### 10.5. Медленные операции при «нормальной» средней загрузке CPU
Сигнатуры: `CPU_HOT_CORE` (одно ядро на 100 % — один поток: checkpoint-thread, exchange-worker, striped-пул на
одной partition, GC-поток), `JAVA_SYS_SHARE` (page faults/THP/futex), `RUNQ_HIGH` при коротких всплесках,
`THP_COMPACTION`. Команды: `cpu` (блок «Ядра»), `cores --sort max`, `java`, `events node01.nmon --metrics
cpu.core_max top.java.sys proc.runq`, `at`. nmon не показывает, какой именно поток горячий — берите thread
dump/JFR.

### 10.6. Кончается место (WAL-архив, снапшоты, логи)
Сигнатуры: `FS_FULL`, `FS_GROWTH` с оценкой времени до 100 %, скачки заполненности в `fs`, растущая запись на
соответствующий диск. Команды: `fs`, `diskmap` (что за диск, сколько осталось), `disk --dev <LV>`.

### 10.7. Подозрение на долгие GC-паузы
nmon не видит GC. Косвенно: `JAVA_CPU_DROP` (JVM встала), либо, наоборот, всплеск `top.java.cpu` со
скачком `cpu.user` на всех ядрах (параллельный GC), `events --metrics top.java.cpu cpu.busy`. Сопоставьте с
`Long JVM pause` в логах Ignite и GC-логами; посмотрите `uarg` (тип GC, Xmx, AlwaysPreTouch).

### 10.8. Память под давлением без swap
Сигнатуры: `MEM_FREE_LOW` и `KSWAPD_ACTIVE` на уровне WARN (с подтверждением), `MAJFAULT_HIGH`, `mem.cached`
падает при росте `top.java.rss`, `disk.read` растёт (страницы читаются с диска вместо кэша), kswapd0 в TOP.
Команды: `mem`, `vm`, `correlate --target vm.pgmajfault`, `timeline node01.nmon --metrics mem.cached mem.free
top.java.rss disk.read`. Для Ignite с persistence это удар по латентности чтений: размер data regions + heap не
должен вытеснять page cache под WAL и файлы partition.

### 10.9. Виртуализация и «соседи»
`CPU_STEAL` > 0 — гипервизор отбирает CPU (переподписка); ищите провалы `top.java.cpu` в те же моменты. Соседи
на самом узле — антивирус/бэкап/мониторинг с высоким CPU или IOwaitTime — блок «Другие процессы» в `java`.

### 10.10. Общая методика по кластеру
1. `info <dir>`, `check <dir>` — доверять ли данным, есть ли разрывы, все ли узлы покрыты.
2. `cluster <dir>` — выбросы, синхронные события, кто закончил раньше, health по хостам.
3. `report <host>` для подозрительных узлов; `at --time` для моментов из логов; `compare` «до/во время».
4. Подсистемные команды по замечаниям; `export` для собственных вычислений.
5. Формулируйте выводы с указанием времени, хоста, метрики, значения и порога — так, как печатает `health`.

## 11. Чего nmon не показывает

- Внутренности JVM: GC-паузы, safepoints, занятость heap/off-heap/metaspace, состояния потоков, per-thread CPU
  (какой пул Ignite горячий), deadlock'и.
- Состояние Ignite: checkpoint buffer, dirty pages ratio, режим WAL, PME, rebalance, роли узлов, координатор.
- Латентность диска за период (await/svctm) — нет без `-D`/DISK*SERV; глубина очереди; fsync-счётчики; ввод-вывод
  по процессам и файлам (какой процесс писал в WAL).
- TCP/UDP: соединения, retransmits, RTT, backlog, ошибки во времени (без NETERROR); кто с кем обменивался
  трафиком; состояние bond/LACP; скорость линка.
- Load average во времени (только на старте), PSI, per-cgroup лимиты и OOM в cgroup, dmesg (OOM-killer, hung
  task, link down), sysctl (swappiness, dirty_ratio, THP mode), ulimit.
- Per-NUMA память во времени, THP/compaction-счётчики, NUMA-локальность.
- Всё короче интервала (10–60 с): 2-секундная пауза GC или 5-секундный fsync-шторм усредняются.
- Часовой пояс и рассинхронизация часов между узлами.
- Процессы ниже порога TOP, короткоживущие процессы между снимками, RSS idle-процессов.
- Ожидание I/O по процессу (IOwaitTime в TOP считается только для главного потока) и достоверные major faults
  процесса (колонка MajorFault в TOP может не согласовываться с системным счётчиком).
- Причины vs следствия: nmon показывает симптомы на уровне ОС; причина подтверждается логами Ignite/JVM.

## 12. Рекомендации по сбору nmon

Для последующего анализа Ignite полезно запускать nmon так:

```bash
nmon -fT -s 30 -c 2880 -m /var/log/nmon      # -T = TOP + командные строки (флаги JVM), 30 с × 24 ч
```

- `-T` вместо `-t`: даёт UARG (флаги JVM, роль процесса).
- Интервал 10–30 с лучше ловит короткие события (checkpoint, всплески); 60 с — минимально приемлемо.
- `-D` (если версия поддерживает) добавляет времена обслуживания дисков (DISKREADSERV/DISKWRITESERV).
- `-g файл_групп` позволяет объединить устройства WAL/persistence/архива в группы (DGBUSY…).
- Синхронизируйте часы узлов (chrony/NTP), иначе кластерный анализ порядка событий недостоверен.
- Не запускайте два nmon одновременно на одном хосте; если запустили — скрипт дедуплицирует, но первый
  интервал каждого файла будет неполным.
